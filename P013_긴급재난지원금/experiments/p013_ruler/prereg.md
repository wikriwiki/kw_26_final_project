# P013 자 만들기 — 후보를 비교하지 않는 라운드. 자를 만든다

**작성 2026-09-23 23:45 · 실행 전 커밋** · 긴급재난지원금 · v5 두 팔 · n=700

---

## 왜 후보를 안 비교하나

지표 25개 중 **프롬프트가 읽히는 자리가 하나뿐**이다(`experiments/ONE_PLACE_LEFT.md`).
후보를 더 만들어도 잴 데가 없다. 막고 있는 것은 프롬프트가 아니라 자다.

긴급재난 P013 은 두 지표가 **자릿수 하나 차이로** 막혀 있다.

```
EM-2  사용가능업종 순효과   필요 n 280  (지금 200)   1.4배
EM-3  전체 카드매출 증가    필요 n 620  (지금 200)   3.1배
```

**둘 다 n=700 이면 닿는다.** 그런데 n 을 올려도 후보를 가를 수는 없다 —
**P013 의 런 간 이동을 한 번도 재 본 적이 없기 때문이다.** 거리두기는 두 번
재서 DS-1 0.2·0.5%p 를 얻었고 그래서 v50·라운드3 의 판정 문턱이 생겼다.
P013 에는 그 수가 없다. 없는 채로 후보를 가르면 잡음을 프롬프트의 성질로 적는다.

그래서 이 라운드는 **같은 프롬프트(v5)를 두 팔로 돌린다.**

## 설계

```
정책   P013 긴급재난지원금 (grant · 2020-05-13 지급)
창     무정책 2020-05-07:05-08(목금) → 정책 2020-05-14:05-15(목금)
       기존 stage3 런과 **같은 창**이다 — 그 n=200 런이 세 번째 관측점이 된다
런     start 2020-05-04 · day0 2020-05-03 · 12일
인원   700명 (EM-3 의 필요 n 620 을 넘긴다)
팔     v5_A · v5_B — **프롬프트도 에이전트도 같다.** 바꾸는 것이 없다
기록   --per-agent 로 에이전트 단위 off/on 을 남긴다
```

## 이 설계가 재는 것과 못 재는 것

**한 스크립트 안의 두 팔은 런 간 이동의 아래끝이다.** v50 과 라운드3 은 하루
간격의 별도 실행이었고 그 사이에 서버 상태·그래프 상태·코드가 달라질 수 있다.
같은 스크립트 안에서 연달아 돌리면 그 차이가 빠진다.

**그것이 이 설계의 요점이다.** 두 수를 가른다.

```
스크립트 안 두 팔의 차이   줄일 수 없는 비결정성 (LLM 동시성·순서)
그보다 큰 실행 간 차이     환경에서 온 것 — **줄일 수 있는 쪽**
```

거리두기에서 0.5%p·2.7%p 가 나왔는데 같은 조건의 두 팔이 거의 안 움직인다면,
**그 이동은 런의 성질이 아니라 실행 사이에 끼어든 무엇**이고 고칠 수 있다.
고치면 **모든 정책에서** 후보를 가를 수 있는 폭이 넓어진다. 한 정책의 문제가
아니다.

에이전트 단위 기록을 남기는 이유가 그것이다. 총합만 보면 어디서 왔는지 모른다 —
같은 사람이 같은 프롬프트로 다른 값을 냈다면 그 자국이 거기 남는다.

## 등록하는 예측

```
EM-3   갈릴 것이다 — 다만 필요 n 620 에 가까워 아슬아슬하다
EM-4   순위. 대상 업종 이름을 고친 뒤 처음 재는 것이라 예측하지 않는다
두 팔   **차이를 예측하지 않는다.** 처음 재는 것이고, 구간을 좁게 적으면
       사후에 맞춘 것처럼 보인다
```

## 채점하지 않는 것

**이 라운드는 프롬프트를 고르지 않는다.** 팔이 둘이지만 같은 프롬프트다.
어느 팔이 정답지에 가까운지 적지 않는다 — 그것은 동전 던지기다.

## 규칙

- 결과를 보고 지표·창·판정식을 고치지 않는다
- 결과를 보고 프롬프트를 고치지 않는다
- 두 팔의 차이는 **다음 라운드의 판정 문턱**으로만 쓴다
