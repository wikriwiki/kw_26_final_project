# 활동 사건 → 정책 입장 → 집단 집계 연결

작성: 2026-09-15. 기반: fe039529 감사 패치 fbe9a58.
작업 브랜치: codex/fe039529-execution-audit.

## 이번에 연결한 실행 경로

1. run_simulation.process_one이 Stage2 선택 결과를 깊은 복사로 보관한다.
2. 기존 소비 엔진·정책 validator가 금액과 결제수단을 확정한다.
3. experience.receipts가 결정 원본과 확정 거래를 분리한 영수증을 생성한다.
4. 기존 night_create_state 호출에서 영수증·관측 기억·입장·입장 변화 이력을 JSON으로 저장한다.
5. 다음 날 기존 Dawn State 조회가 관측과 입장을 읽는다.
6. 기존 Stage1의 사용자 입력에 관측과 이전 입장 요약을 추가한다. 호출 횟수는 늘리지 않는다.
7. Stage1이 선택적으로 policy_appraisals를 반환한다. 사건 ID·시각·정책·본인·페르소나 필드를 검증한다.
8. 채택된 입장과 기각 진단이 일일 metrics에 저장된다. report_experience가 집단별로 집계한다.

관측은 State에 저장되는 별도의 경험 기억이다. 기존 visited Memory의 만족도 필터에 의존하지 않으므로 구매가 축소되거나 0원이 된 거래도 관측으로 전달된다. 다만 0원 거래가 곧 방문 실패라는 의미는 아니다.

## 기록 계약

- execution_receipts_json: 일자별 전체 영수증. event_id, 원래 결정 금액·요청 수단, 확정 금액, 자기부담, 구매 상태, 정책별 적용 가능 여부·결제액, 시스템 진단.
- observations_json: 최근 최대 8개 거래 사실. 원래 reasoning이나 시스템 오류는 제외한다.
- policy_appraisals_json: 정책별 최신 입장, 표현된 이유, 근거 ID, 페르소나 근거, 실제 측정일.
- appraisal_changes_json: 이전 입장과 새 입장의 변화 이력.
- metrics: 위 영수증·입장·변화·기각 진단과 run/day/group 정보를 함께 보존.

영수증 ID는 run namespace+agent+day+event 위치의 안정 해시다. SIM_RUN_ID가 있으면 사용하고 없으면 출력 디렉터리 절대경로를 사용한다. 별도 실험에는 반드시 다른 SIM_RUN_ID와 SIM_OUTPUT_DIR를 쓰고 DB도 기존 격리 규칙을 적용해야 한다. 이번 패치만으로 Neo4j 전체 실험 격리가 완료된 것은 아니다.

## 입장을 생성·채택하는 조건

- 자기 자신의, 오늘보다 이전에 관측한 거래만 근거가 된다.
- 해당 정책이 거래의 policy_facts에 있어야 한다.
- 페르소나 참조는 실제 존재하는 필드여야 한다.
- stance는 support/oppose/mixed/uncertain 중 하나.
- 외부에 표현할 이유는 300자 이하, 사건 ID와 페르소나 참조는 각각 1~3개.
- 갱신은 호출당 최대 3개만 처리한다.
- 업데이트가 없으면 이전 입장과 기존 측정일을 그대로 유지한다.
- 미응답·미측정은 uncertain 또는 중립으로 자동 변환하지 않는다.
- malformed 입장 메타데이터 때문에 정상 일일 계획을 재생성하지 않는다.
- 적용 불가능한 LLM 결제 요청은 시스템 진단이다. 실제 시민이 거절당했다는 사건으로 바꾸지 않는다.

검증은 참조·구조·시간 정합성이다. 자연어 이유의 모든 의미가 근거로 입증되거나 인과관계가 확인되었다는 뜻은 아니다. 인터뷰와 보고서에서도 이 차이를 유지해야 한다.

## 시간과 비용

- 오늘 실행한 거래는 다음 날 Stage1에서 해석한다.
- 마지막 날 거래에 대한 입장은 다음 Dawn을 실행하지 않았다면 아직 미측정이다.
- 관측 입력은 최대 8개, 직렬화된 관측 부분은 5,000문자까지다. 이전 입장은 관련 정책의 stance/as_of만 전달한다.
- LLM 호출 추가 없음. 입력·출력 토큰과 JSON 저장 용량은 증가할 수 있다.
- 모든 거래마다 이유를 강제로 생성하지 않는다. 변화가 필요할 때만 짧은 표현을 받는다.

## 집계 실행

```powershell
python scripts/sim/report_experience.py --run-dir <실행디렉터리> --day 2026-09-15 --group-by income --out <결과경로.json>
```

group-by: income / job / life_stage.
해당 날짜의 완료된 agent snapshot을 중복 제거해 정책별·집단별 stance 수, 측정 수, 미측정 수, 입장 측정일 분포를 반환한다. 실패자 수·schema 누락·잘못된 로그 수도 품질 정보로 구분한다. 서로 다른 run_id가 섞이면 집계를 거부한다.

이는 시뮬레이션 에이전트의 표현된 입장 분포이며 실제 여론 정확도나 인간 설문에 대한 검증 성능이 아니다. 예정 전체 인구 대비 결측률은 실행 manifest가 따로 필요하다.

## 현재 지원 범위와 남은 일

지원: 기존 소비 엔진이 확정한 구매·정책지갑 grant 결제 결과에서 입장과 집계까지의 연결.
미지원: 실행 엔진이 없는 이동·대기·재고·대화 수신·접수 거절 경험, 모든 정책 기전의 일반화, 발표 직후 사전 입장 측정, 인간 설문 정확도 보장.

정책별 적용 가능 여부도 현재 소비 엔진이 표현하는 사용처·업종 규칙 범위다. 정책의 모든 법적 자격 조건을 구현했다는 뜻은 아니다. grant 이외 기전은 해당 환경 실행 어댑터가 실제 결과를 생성한 뒤 동일 observation 계약에 연결해야 한다.

## 검증

새 테스트는 영수증과 결정 분리, 미래/타인/다른 정책/존재하지 않는 근거 거부, 미인지·미측정 구분, 이전 측정일 유지, 혼합 run 거부, 중복·실패 집계, malformed 메타데이터 처리 등을 확인한다.

두 날짜 runner 테스트에서는 실제 process_one·소비·정책 validator·경험 갱신·metrics 경로를 실행하고 DB/LLM 경계만 대체했다. 첫날 거래 ID가 다음 날 입장 근거로 저장되고 집단 집계에서 1명으로 측정됨을 검증했다. Stage1/Stage2 호출은 각각 하루 한 번이었다.

실제 Neo4j 및 GPU 통합 실행은 아직 하지 않았다. 저장된 State JSON의 실제 DB 왕복과 운영 모델이 새 optional 필드를 안정적으로 출력하는지는 소규모 실험에서 확인해야 한다.
