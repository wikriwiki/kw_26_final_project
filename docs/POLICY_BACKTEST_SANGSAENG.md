## 0. 정책이 뭔가

**상생소비지원금**은 2021년 10~11월, 코로나19로 위축된 소비를 진작하기 위해 정부가 시행한 카드 캐시백 사업이다.

- **(시행시기)** 2021.10.1 ~ 11.30 (2개월)
- **(사업규모)** 7천억원 계획 → 실제 집행 8,054.2억원
- **(지원대상)** ❶만 19세 이상(2002.12.31 이전 출생) ❷2021년 2분기(4~6월) 중 본인 명의 신용·체크카드 사용실적 있는 자(외국인 포함, 비소비성 지출 제외)
- **(지원방식)** 월간 카드 사용액이 **2분기 월평균 대비 3% 이상 증가 시, 초과분의 10%를 캐시백**으로 환급
  - 예: 2분기 월평균 100만·10월 153만 → 증가 53만 중 3만(3%) 제외한 50만의 10% = **5만원**
- **(지원한도)** 1인당 월별 **10만원 한도**
- **(대상소비)** 적립업종만 실적 산정(네거티브 방식). 제외 = 대형마트·대형백화점(아울렛·복합몰 포함)·면세점·대형전자전문점·대형종합온라인몰·홈쇼핑·유흥·사행·신차구입·명품전문매장·실외골프장·비소비성지출(연회비·세금·보험·상품권 등) — 비소비성 제외 카드사용액의 약 80%가 실적 인정 대상
- **(지급 타이밍)** 10월 소비 → 캐시백 **11/15** 지급 / 11월 소비 → 캐시백 **12/15** 지급. 유효기간 ~2022.6.30
- **(전담기관)** 9개 카드사(롯데·비씨·삼성·신한·우리·하나·현대·KB국민·NH농협)

## 1. 정책의 취지 — "돈 지급"이 아니라 "가격 유인"

상생소비지원금은 정액 현금을 주는 정책이 **아니다**. 2분기보다 더 쓰면 초과분의 10%를 돌려주는 **가격 유인** 정책이다.

- **목적**: 피해 누적 업종(=적립업종, 소상공인 중심)의 소비 회복 + 전체 소비 진작.
- **메커니즘**: 적립업종의 상대가격을 사실상 10% 낮춤 → 적립업종으로 소비 이동(대체효과) + 실질소득 증가(소득효과). 제외업종은 소득효과(+)와 대체효과(−)가 상쇄되어 부호가 이론상 불확실.
- **핵심 타이밍**: 캐시백은 다음 달 15일 지급. 쓰는 시점엔 아직 돈을 손에 쥐지 않는다. 10월 소비 증가가 있다면 그건 "받은 돈" 때문이 아니라 **"10% 돌려받을 기대(anticipation)"** 때문 — **우리가 재현할 것은 이 기대효과다.**

### 버는 쪽 vs 쓰는 쪽 (혼동 주의)

| 단계 | 규칙 |
|---|---|
| 버는 것(실적 산정) | 제외업종 소비는 실적에 **안 잡힘** — 거기서 써도 캐시백이 늘지 않음 |
| 쓰는 것(받은 캐시백 사용) | **제한 없음** — 모든 국내 가맹점(제외업종 포함) 사용 가능 |

### 실제 관측 효과 (보고서 실측, 요약부)

- 적립업종: **크게 증가**
- 제외업종: **≈0 (그대로~미세 증가)** — "감소"가 아님
- 총량: **증가**(승수 165%, 다만 §5.3에서 채점 대상 제외 사유 설명) — "총량 그대로 방향만 전환"이 아니라 순증가

## 2. 소비쿠폰(EXP-001 / P010)과의 결정적 차이

EXP-001(민생회복 소비쿠폰, 정책 ID **P010**, `type: "grant"`)을 이미 완주했지만, 상생소비지원금은 그것과 **다른 능력**을 시험한다.

| | 민생회복 소비쿠폰 (P010, grant) | **상생소비지원금 (본 백테스트)** |
|---|---|---|
| 돈 성격 | 선지급 정액 쿠폰(정책지갑) | 사후 캐시백(더 쓴 만큼, 익월 지급) |
| 금액 결정 | 외생 = 입력값(소비 10분위별 15/30/40만) | 내생 = 행동의 출력(사후 계산) |
| 사용처 제한 | `poi_restricted=true` → 쿠폰 사용처만 결제 가능 | 버는 쪽만 제한, 쓰는 쪽은 무제한 |
| 측정 대상 | 받은 돈을 얼마나 쓰나 (**MPC**) | 인센티브에 반응해 **얼마나 더 쓰나** (기대효과) |
| 지배 역학 | 정책지갑을 **개인부담 대신 우선 결제**(사후 정산) | **한계 인센티브 / 상대가격 반응**(대체+소득효과) |
| 우리 엔진 주 채널 | 정책지갑 사후 정산(`settle_policy_spend_priority`) | 선택 유인(자연어 신호 → 대체효과) |
| 시뮬 시험 능력 | 지급 자산의 결제·정산 충실도 | **행동 반응 충실도 = LLM 자연어 채널의 진짜 테스트** |

### ⚠️ 소비쿠폰 메커니즘이 21일 커밋으로 바뀐 점 (§2 논리의 근거)

EXP-001 역사 결과에서 시뮬 MPC가 실측(0.20) 대비 ≈1.0으로 발산했다([EXP001_VALIDATION_vs_BOK.md](EXP001_VALIDATION_vs_BOK.md), [EXP001_CAVEATS.md](EXP001_CAVEATS.md)). **이 발산을 고치려고** 21일 커밋이 소비모델을 바꿨다:

- `available_today`는 정책지갑 잔액을 **총소비 예산에 더하지 않는다**(`p × 지원금잔액` 강제 인출 폐기).
- `spend_today`는 `grant_part=0`을 반환 — 총소비는 오직 개인예산(성향×평상 소비앵커)에서 나온다.
- 정책지갑은 **실제 거래가 확정된 뒤** `settle_policy_spend_priority`(+ max-flow `_allocate_policy_capacity`)로 사후 정산되어, **이미 정해진 거래의 개인부담만 대체**할 뿐 총액을 늘리지 않는다.

즉 이제는 **소비쿠폰조차 "지갑을 비워서 총소비를 부풀리는" 모델이 아니다.** 그럼에도 상생소비지원금은 여전히 **다른 것**을 시험한다: 소비쿠폰은 관측창 안에 지급된 자산을 "결제·정산"하는 채널을 검증하지만, 상생지원금은 **관측창 안에 아무 돈도 없는 상태에서 가격 유인(기대효과)만으로 소비를 얼마나 늘리는가**를 검증한다. 정책지갑 자체가 없으므로 사후 정산 경로도 개입하지 않는다. → 자연어 채널이 상대가격 신호를 소비 행동으로 옮기는지가 이 백테스트의 차별적 가치다.

## 4. 정책 주입 설계 (우리 엔진 맞춤)

소비쿠폰과 다르게 — 정책지갑 사후 정산이 아니라 **선택 유인(대체효과)이 주 채널**이며, **관측창 안에서 정책지갑을 아예 만들지 않는다(현금 0).**

```
전기간 (OFF / A런):  정책 없음 → 각 에이전트 평소 소비 = baseline 관찰
주입 (day 0):        정책지갑 없음(캐시백 0). 전원에게 "유인 신호"만 제공
                      ⓐ 라벨: sangsaeng_eligible 백필 (제외리스트 = §0 규칙)
                      ⓑ Dawn 컨텍스트: 에이전트별 실제 숫자를 자연어로 고지
                         "네 2분기 월평균 카드소비 X원, 이번 달 누적 Y원,
                          3% 문턱 Z원. 적립업종(대형마트·백화점·대형온라인몰
                          제외 대부분)에서 더 쓰면 초과분 10%를 다음 달에
                          돌려받아(월 최대 10만원)."
                      ⓒ 정렬 가점·강제 넛지 없음(POLICY_POI_SORT_BOOST=0 유지) —
                         카테고리/POI 선택은 전적으로 Stage1/2 LLM 자율
후기간 (ON / B런):    같은 시드로 유인 신호만 걸고 재실행 → 반응 관찰
```

### 4.1 왜 "정책지갑"도 "정렬 가점"도 안 쓰는가

- **정책지갑(캐시백 즉시 지급) 배제**: 실제로도 캐시백은 익월 지급이라 관측창 밖이다. 21일 커밋 이후엔 지갑이 총소비를 부풀리진 않지만(`settle_policy_spend_priority`는 개인부담을 사후 대체만 함), 지금 지갑을 만들면 검증 채널이 "가격 유인 반응"이 아니라 "지급 자산의 결제·정산"으로 바뀌어 §2의 차별점 전제가 깨진다. → 상생 정책 JSON에는 `decile_grants`/`income_grants`/`poi_restricted`(쿠폰 지갑 트리거)를 **넣지 않는다**(§9 G3).
- **정렬 가점(Stage2 적립매장 순위 부스트) 배제**: 이건 C1/D1이 검증하려는 답("적립업종 선택 증가")을 우리가 직접 손으로 심는 것이라 **순환논증**이다. 현 코드는 정렬 가점을 `POLICY_POI_SORT_BOOST` 환경변수로 노출하고 **기본값이 "0"**이다(`stage2_poi.py:273`, `run_simulation.py:307`). 본런은 이 기본값(0)을 그대로 유지한다 — `=1`은 별도 민감도 실험 전용이며 백테스트 본런에서는 절대 켜지 않는다.

### 4.2 무반응(null) 리스크 대응 — 프리플라이트 없이 단발 런에서

프리플라이트(소규모 탐침)를 생략하기로 했으므로, "반응 없으면 조건부로 보강한다"는 트리거 자체가 없다. 그래서 안전장치를 **본런 설계 자체에 사전 내장**한다. 단, "결과를 유리하게 만드는" 장치가 아니라 **"신호 전달력·통계적 검출력"만 높이는** 장치여야 순환논증을 피한다.

1. **구체 숫자 주입 (신호 전달력)**: 뭉뚱그린 정책 설명이 아니라 에이전트별 실제 2분기 월평균·이번달 누적·문턱 숫자를 Dawn 프롬프트에 직접 준다(§4 ⓑ). 무반응의 실제 흔한 원인은 "이해를 못 했다/못 봤다"이지 "이해했는데 무시했다"가 아니다 — 이걸 최소화한다. 이 숫자들은 정책이 정한 고정 파라미터(1.03배, 10%, 10만원)이지 우리가 결과 보고 조정하는 값이 아니다.
2. **관측창·표본 크기 (검출력)**: 최소 **2주**, 가능하면 **1개월**(권장, EXP-001의 관측창 과소 교훈 승계). 표본은 `spending_level_wd`(소비 10분위) 균형표집으로 소규모 실제 효과도 검출 가능한 크기 확보. 결과를 만드는 게 아니라 실제로 있는 효과를 "놓치지 않는" 조치.
3. **하지 않는 것**: 실제 10% 상대가격을 소비모델 수식에 직접 반영하는 방식(가격탄력성 내장)은 **채택하지 않는다** — 탄력성 파라미터 자체가 답을 내장할 위험이 있고, 검증할 트리거(프리플라이트 null 확인) 없이 넣으면 "왜 넣었는지"를 사후에 정당화하기 어렵다. 반응이 없다면 그것 자체가 유효한(부정적) 결과로 §8에 기록한다.

### 4.3 카테고리 매핑 + "제외 arm 부재"라는 구조적 현실

우리 POI는 **소상공인 물리매장 12 L1 분류**다(`categories.yaml`). 상생 적립/제외를 우리 카테고리에 얹으면:

**(1) KDI 8개 적립 업종 → 우리 L1(L2) — D1/D2 채점용 매핑**

| KDI 적립 업종 | 우리 L1 (L2 예시) |
|---|---|
| 가전·가구 | 쇼핑(가구, 가전·통신) |
| 학원 | 교육(학원, 교육지원, 기타교육) |
| 이·미용 | 미용(미용실·네일·피부관리 등 전체) |
| 여행·레저 | 여가(여행사·스포츠·유원지·오락·볼링·당구·노래방) + 기타(숙박) |
| 요식 | 식사 + 카페 + 디저트 + 주점(일반주점·호프) |
| 유통 | 마트 + 편의점 + 쇼핑 일반소매(의류·생활용품·화장품·문구 등) |
| 기타 | 건강(병원·약국·의원·치과) + 기타 서비스(주유소·세탁·수리·차량정비) |

**(2) 상생 제외 업종 → 우리 데이터: 거의 전부 부재**

| 상생 제외 | 우리 매핑 방법 | 데이터 존재 |
|---|---|---|
| 대형마트·SSM·백화점·복합몰·아울렛 | 상호명 브랜드 룰(이마트·홈플러스·롯데마트·코스트코·백화점…) | 극소수(소상공인 DB라 거의 없음) |
| 대형 전자전문점 | 상호명(하이마트·전자랜드·디지털프라자·베스트샵) | 극소수 |
| **대형종합 온라인몰** | — | **없음(물리 POI만 존재)** |
| 명품전문매장 | 시계·귀금속 L2 + 명품 상호명 | 명품관 없음 |
| **신차구입** | 신차 딜러 | **없음**(자동차부품·차량정비는 적립) |
| 유흥·사행 | 상호명(단란주점·유흥주점·룸살롱·카지노·복권) | 극소수 |

→ **구조적 현실: 우리 POI ≈ 전부 적립업종이다.** 제외로 뺄 수 있는 건 상호명 룰로 잡히는 극소수(대형 브랜드·유흥)뿐이고, 온라인·대형·명품·신차는 아예 없다. 이는 §8의 한계이자 §6의 검증 설계를 바꾸는 핵심 제약이다 — "적립 vs 제외" 대비(C1)는 제외 표본이 없어 검증 불가에 가깝고, 상생 효과는 우리 시뮬에서 사실상 **"적립업종(=거의 전부) 소비 순증"**으로 환원된다.

**(3) 라벨 주의**: 상생 적립/제외는 POI의 `coupon_eligible`(소비쿠폰용)과 **다르다** — 상생 적립이 훨씬 넓다(프랜차이즈 직영·대형 병원/학원/가구도 적립 인정). `coupon_eligibility.py`의 `_NAME_EXCLUDE`(대형·직영 브랜드)·`_NAME_VICE`(유흥·사행) 상호명 룰은 **재사용하되**, 소비쿠폰이 뺐던 프랜차이즈 직영(스타벅스·올리브영·다이소)은 상생에선 **적립으로 되돌린다**. 결과는 새 속성 `sangsaeng_eligible`로 별도 기록(§9 G1).

### 4.4 기대효과만으로 반응할까 — 이 백테스트의 근본 리스크와 대응

**현금을 관측창 안에 한 푼도 안 주고 자연어 신호만으로** 소비를 유도하는 설계라, 에이전트가 실제로 반응할지가 근본적으로 불확실하다. 실측 보고서와 대조했을 때 부호조차 안 맞는 결과가 나올 수 있다. 이 리스크를 없앨 수는 없고, **정직하게 다룬다**:

1. **애초에 이게 시험 대상이다**: "LLM 자연어 채널이 순수 가격 유인(기대효과)을 소비 행동으로 옮기는가"가 본 백테스트가 던지는 질문이다. 반응이 약하거나 없다면, 그건 백테스트의 버그가 아니라 **에이전트에 대한 유효한 발견**이다(§8-7). null도 결과다.
2. **크기는 절대 안 맞춘다**: 우리 관측창(2주~1개월, 기대효과만) vs 보고서(2개월+캐시백 이월사용까지). 부호·방향·순위만 본다(§6). "서울 +14.57%"를 우리가 재현한다는 주장은 애초에 하지 않는다.
3. **신호 전달력만 최대화(순환논증 회피)**: 구체 숫자(2Q 월평균·이번달 누적·문턱)를 프롬프트에 직접 준다(§4.2). "이해 못 함"으로 인한 무반응만 줄이고, 반응의 크기·방향은 손대지 않는다.
4. **검증 항목을 실현 가능한 소수로 좁힌다**(§6): 우리 POI가 거의 전부 적립이라, 무리하게 4개(C1·C2·D1·D2)를 다 채점하지 않는다. 실현 가능한 **C2(총소비 방향) 1개를 축으로**, D1(업종 순위)은 나오면 보고하는 식으로 간다.

## 5. 검증 방법 — 보고서 DiD를 재현하는 게 아니라 정답으로 대조

### 5.1 대조군 설계: B−A가 보고서 DiD보다 깨끗하다

보고서는 같은 집을 두 번 못 돌리니 **받은 집(수급) − 못 받은 집(미수급)**을 비교한다. 하지만 수급/미수급은 원래 다른 사람들이라 자기선택 편향이 생기고, 보고서는 DDD·IV로 힘들게 보정한다.

**우리는 이럴 필요가 없다.** 시뮬이라 같은 에이전트를 두 번 돌릴 수 있다:
- **A런** = 정책 끔 / **B런** = 정책 켬 (같은 시드, 같은 에이전트)
- **B − A = 순수 정책효과** ← 이게 우리의 "DiD"

같은 시드로 OFF/ON을 돌리는 근거는 엔진에 이미 있다: `dawn_context.py:POLICY_CYPHER`가 활성 정책을 자동 픽업하므로, 정책 노드 존재 여부만으로 반사실(OFF/ON)이 성립한다. 대조군이 "못 받은 다른 집"이 아니라 **"정책 없는 평행우주의 같은 집(A런)"**이라 자기선택이 없다.

| | 보고서 | 우리 |
|---|---|---|
| 대조군 | 미수급가구(다른 집) | A런(같은 에이전트, 정책 없음) |
| 방법 | DiD / DDD / IV | 같은 시드 **B − A** |
| 편향 | 자기선택 있음 → 보정 필요 | 없음(같은 사람) |
| 결과물 | 계수 = 정답 | B − A = 우리 예측 |

→ **수급/미수급으로 나눌 필요 없음.** 우리 정책 신호는 전원에게 동일하게 노출되므로 자연적 미수급군이 없다. 우리는 보고서의 *방법*을 재현하는 게 아니라, 보고서가 그 방법으로 *이미 낸 정답*을 우리 B−A와 대조한다.

### 5.2 3층 구조 (메모리 `backtest-policy-cases` 승계)

- **Layer 1 (정답 벡터)**: KDI PDF 표에서 직접 추출 = §3. 원자료(KCB·신한) 미보유 → 우리가 DiD를 재계산하지 않는다. PDF 표 자체가 정답지.
- **Layer 2 (시뮬 예측 벡터)**: 같은 시드 A(OFF)/B(ON) 2런 → B−A.
- **Layer 3 (채점)**: Layer2를 §6 벡터로 산출 → Layer1과 대조 + 내적 타당성(§7).

### 5.3 시간축·규모

baseline(2Q 월평균)은 **데이터 앵커(`s_daily_wd`)라 시뮬 불필요** → A/B런은 처치기간만 돌리면 된다. 관측창 ≥2주, 권장 1개월(§4.2). 표본은 `spending_level_wd` 10분위 균형표집(비용 대비 검출력 확보를 위해 2,000~3,000명 선에서 시작, 필요시 확대).

**승수(165%, 표4-11)는 채점하지 않는다** — 우리 관측창(2주~1개월)과 보고서 시간축(2개월+캐시백 이월사용까지 포함)이 달라 절대 크기 대조가 무의미하다. §3에 참고로만 남긴다.

## 6. 무엇을 예측·검증하나

시뮬 예측 = 같은 시드 **B(ON) − A(OFF)**. 비교는 **숫자 크기가 아니라 부호·순위·방향**만 본다(크기 대조 안 함, §4.4-2). **모든 항목을 다 채점하지 않는다** — 우리 POI가 거의 전부 적립업종(§4.3)이라 실현 가능한 것만 골라 축소했다.

### 6.1 필수(축) — 이거 하나면 1차 성공 판정 가능

| # | 검증 | 정답 | 판정 기준 |
|---|---|---|---|
| **C2** | **총소비가 정책 ON에서 증가하는가**(부호 +) | 표4-6 서울 열(10월 +14.57%), 표4-4 전국(+11.25%) | B−A 총소비 > 0 이면 통과. 크기는 대조 안 함(시간축·기대효과 한정) |

우리 POI가 사실상 전부 적립이므로 상생 효과는 시뮬에서 **적립업종 소비 순증 = 총소비 순증**으로 환원된다(§4.3). 따라서 C2가 이 백테스트의 실질 헤드라인이다.

### 6.2 보조(창발이면 보고, 게이트 안 함)

| # | 검증 | 정답 | 판정 기준 |
|---|---|---|---|
| **D1** | 업종 순위 | 표4-7 10월열 | 카테고리별 B−A를 정렬 → 가전·가구(내구재)가 상위군, 학원·이·미용이 하위군인지. 상위군/하위군 구분만(1·2위 정밀 일치 불필요). **창발이면 강한 증거**, 단 2주 창에서 내구재 거래가 희소해 노이즈 큼 |

### 6.3 검증하지 않거나 탐색적으로만

- **C1(적립↑ AND 제외≈0)**: 게이트에서 제외. 우리 POI에 제외업종 표본이 사실상 없어(§4.3) placebo가 성립하지 않는다. 극소수 제외 POI 매출을 참고로 리포트에 붙이되 판정엔 쓰지 않는다.
- **D2(소득별 재배분: 저소득=요식/유통, 고소득=가전/학원)**: 탐색적으로만. 이론상 판별력 최상(정렬가점으로도 흉내 불가)이지만, 소득 차등 반응이 기대효과만으로 창발하기는 가장 어렵다. 나오면 보너스로 보고, null이어도 실패로 판정하지 않는다.

**핵심**: 1차 성공 = **C2 통과**(총소비 방향 +). D1이 창발로 함께 나오면 강한 증거. C1·D2는 판정 게이트가 아니라 탐색적 관찰이다. 무반응(§4.4·§8-7)도 유효한 결과로 기록한다.

## 7. 내적 타당성

- **평행추세**: 처치 직전 pre-period(A런 관측 구간)에서 카테고리별 소비 분포가 안정적인지 확인.
- **Placebo**: 실적**제외**업종 효과 ≈0 — 단 우리 POI에 제외 표본이 사실상 없어(§4.3) placebo 검증력은 약하다. 잡히는 극소수(대형 브랜드·유흥 상호명) 매출만 참고로 확인.
- **중립성 게이트**: `scripts/sim/policy_preflight.py`로 주입 전 점검. 이 스크립트는 docstring에 "행동 파라미터(소비성향 클램프·가격 탄력·정렬 가점 등)는 절대 건드리지 않는다"를 명문화하고 입력 표현·주입 배선만 점검한다. 상생 JSON에 정렬가점·지갑 필드가 없음을 코드 리뷰로 재확인하고, `check_db_wiring`으로 `applied_to`>0(정책 노출 배선)을 실측 게이트한다.

## 8. 한계 (반드시 리포트에 명시)

1. **서울 전용 정밀 정답은 C2(표4-6 서울 열) 하나뿐** — 업종(D1)·소득(D2)은 전국 풀링 수치라 순위·방향만 대조 가능, 크기 대조 불가.
2. **시간지평 불일치**: 시뮬 2주~1개월 vs 보고서 2개월+이월사용 → 절대 크기(승수 165%, DDD 정밀치) 검증은 하지 않음(§5.3).
3. **제외 arm 사실상 부재(가장 큰 구조적 한계)**: 우리 POI는 소상공인 물리매장뿐이라 상생 제외업종(대형마트·백화점·대형전자)이 극소수, 대형종합온라인몰·신차는 아예 없음(§4.3). → **"적립 vs 제외" 대비(C1)가 성립하지 않아** 검증 게이트에서 뺐고(§6.3), 상생 효과를 총소비 순증(C2)으로만 근사한다. 방향 유인은 재현하되 상대가격의 업종 간 전환 크기는 검증 불가.
4. **공간(자치구별)·재정승수(크기)는 이 케이스 몫이 아님** — 다른 백테스트 케이스(소비쿠폰/상권분석)가 담당.
5. **페르소나 시점(2023~24) vs 정답 시점(2021)** 격차 존재.
6. **가구원수 속성 부재**: 표4-5(4인가구 최대) 검증은 스코프에서 제외(§3 "안 봐도 되는 표").
7. **무반응 리스크(§4.2)**: 프리플라이트를 생략한 단발 런이므로, D1/D2가 null로 나올 가능성을 배제할 수 없다. null 자체도 "현재 자연어 채널로는 상대가격 유인이 전달되지 않는다"는 유효한 결과로 기록하고, 사후에 사후분석(신호가 실제로 프롬프트에 도달했는지 로그 확인, `timing_metrics.py`의 정책 블록 렌더 확인 포함)으로 원인을 진단한다 — 이 경우에도 사후에 정렬 가점을 소급 적용해 "성공"으로 재포장하지 않는다.
8. **카드=전체지출 프록시**: 에이전트 스키마에 결제수단 필드가 없어 `actual_spent`를 카드결제로 근사(현금 구분 불가).

## 9. 시뮬 갭 & 구현 지점

**이미 있는 것 (재사용)**
- 정책 주입: Neo4j `:Policy` 노드 + `applied_to`(서울 전역 → 25개 자치구 확장) 엣지, `dawn_context.py:POLICY_CYPHER`(활성정책 자동 픽업 = OFF/ON 반사실의 근거). POLICY_CYPHER는 현재 `income_grants`·`decile_grants`·`grant_key` 등 grant 확장 필드까지 반환하지만, 상생 JSON은 이 필드들을 비워 두므로 grant 경로가 활성화되지 않는다.
- 소비 모델: `scripts/sim/consumption.py` — `spend_today`가 `grant_part=0`(개인예산만으로 총소비 결정), `settle_policy_spend_priority`가 정책지갑을 사후 정산(개인부담 대체, **총액 미증가**). **상생은 정책지갑이 없으므로 이 정산 경로가 no-op**이 되고, `_envelope_match`(사용처 제한 필터)도 우회된다 → 순수 자연어 채널만 남는다.
- 사용처 판정 패턴(참고용, 값 재사용 금지): `scripts/sim/coupon_eligibility.py` + `scripts/neo4j_load/09_coupon_eligibility.py` — 순수룰·백필 구조는 참고하되 라벨 값은 상생과 다름(§4.3).
- 집계: `scripts/sim/evaluate.py`(전후 매출 DID), `analyze_policy_spend.py`(정책×카테고리/소득/자치구/일자).
- 검증 프로토콜: `POLICY_BACKTEST_BOK_ALIGNMENT.md`(사전등록 원칙, 중립성 황금률), `policy_preflight.py`.

**갭 (신규 구현 필요)**
- **G1 — 상생 전용 업종 맵**: `scripts/sim/sangsaeng_eligibility.py`(신규). `coupon_eligibility.py`의 상호명 룰(`_NAME_EXCLUDE`·`_NAME_VICE`)은 재사용하되 프랜차이즈 직영은 적립으로 되돌리는 등 상생 기준으로 완화(§4.3). POI 백필은 `09_coupon_eligibility.py` 패턴 참고, **별도 속성 `sangsaeng_eligible`**로 기록. **주의: 백필 결과는 거의 전부 True가 정상**(우리 POI≈전부 적립, §4.3) — 이건 버그가 아니라 데이터 현실이다. 업종 매핑표 `data/sangsaeng/industry_map.json`(우리 POI L1/L2 → KDI 8개 업종, §4.3 표 (1) 그대로, D1 채점에 필수).
- **G2 — Dawn 자연어 고지**: `dawn_context.py` 확장. 현재 정책 카드는 `_format_policy`(호환 래퍼) = `_format_policy_facts`(정책 공통 사실) + `_format_policy_status`(개인 상태)로 분화돼 있다. 상생의 에이전트별 실제 숫자(2Q 월평균·이번달 누적·문턱)는 `_format_policy_status` 쪽에 얹는다(§4 ⓑ). **지갑/봉투 로직 변경 없음 — 순수 정보 제공.**
- **G3 — 정책 JSON**: `data/neo4j_load/policies/P012.json`(신규, 파일명은 기존 관례대로 순수 `P0NN.json`). 현재 `grant` 타입이 정식 존재(P010=쿠폰)하지만, **상생은 grant가 아니다** — 지갑을 만들지 않는 **새 타입**(예: `cashback`/`incentive`)으로 신설하고 `decile_grants`·`income_grants`·`poi_restricted`(쿠폰 지갑·`[쿠폰]` 마커·하드검증 트리거)를 **전부 비운다**. `benefit_rate: 0.10`, `threshold_ratio: 1.03`, `cap_per_agent: 100000`은 오직 프롬프트 텍스트 생성용 메타데이터로만 쓴다. 적립 마커가 필요하면 쿠폰용 `poi_restricted` 경로 대신 별도 `[적립]` 표시 플래그를 둔다(지갑 미생성).
- **G3b — 로더**: 상생은 non-grant이므로 grant 확장 로더(`10_load_grant_policy.py`, income/decile/applied_to 세팅)를 그대로 쓸 수 없다. `:Policy` 코어 필드 + `applied_to`(25개 자치구) 엣지를 만드는 경로가 필요(`policy_pipeline`/`neo4j_writer` 재사용 또는 로더 확장). preflight `check_db_wiring`이 `applied_to`>0을 게이트하므로 여기서 반드시 통과.
- **G4 — 기간 집계**: `evaluate.py` 확장 또는 `scripts/sim/aggregate_period.py`(신규) — 일별 매출을 관측창 전체로 재집계, `sangsaeng_eligible`·소득분위·카테고리 교차.
- **G5 — 상생 전용 채점기**: `scripts/sim/validate_sangsaeng.py`(신규, BOK 문서가 예고한 `validate_policy_did.py`의 상생판). §6 벡터 산출 + 판정.

## 10. 구현 순서 (마일스톤)

1. **M1 업종 맵**: `sangsaeng_eligibility.py` + `industry_map.json` + `sangsaeng_eligible` 백필 → 자체 테스트(코드 내 케이스, `coupon_eligibility.py` 자체테스트 패턴 승계).
2. **M2 Dawn 고지 + 정책 JSON**: `_format_policy_status` 확장 + `P012.json`(new type, 지갑 필드 없음). 프롬프트 렌더링 결과를 사람이 눈으로 확인(실제 에이전트 몇 명 샘플로 문구 검수).
3. **M3 로더 + 중립성 게이트**: non-grant 로더로 `:Policy`+`applied_to` 적재 → `policy_preflight.py` 통과 확인(정렬가점 없음=`POLICY_POI_SORT_BOOST` 미설정, 지갑 필드 없음, `applied_to`>0을 코드 리뷰·DB 실측으로 재확인).
4. **M4 기간 집계·채점기**: `aggregate_period.py`/`evaluate.py` 확장 + `validate_sangsaeng.py` — §6 벡터 산출 로직만 먼저 완성(A/B 데이터 없이도 더미로 단위테스트 가능하게).
5. **M5 본런**: 표본(2,000~3,000명, `spending_level_wd` 균형) × 관측창(2주~1개월) OFF/ON, 같은 시드, **`POLICY_POI_SORT_BOOST=0`(기본)**. **단발 — 여기서 재시도 없음을 전제로 M1~M4를 충분히 검증 후 진입.**
6. **M6 채점·리포트**: `validate_sangsaeng.py --off <A_run> --on <B_run>` → §6 표 + §8 한계 포함 리포트 `output/sim/report/SANGSAENG_BACKTEST.{md,json}`.

## 11. 검증 방법 (end-to-end)

```bash
# M1 업종룰 자체 테스트
python scripts/sim/sangsaeng_eligibility.py            # ALL OK

# M2 Dawn 고지 문구 샘플 검수 (실제 실행 전 육안 확인)
python scripts/sim/dawn_context.py --agent <sample_id> --dry-run

# M3 중립성 게이트 (지갑 필드 없음·applied_to 배선 확인)
python scripts/sim/policy_preflight.py data/neo4j_load/policies/P012.json

# M5 본런 (같은 시드, 단발, 정렬가점 OFF)
POLICY_POI_SORT_BOOST=0 python scripts/sim/run_simulation.py --start <date> --days <14~30> --seed 42   # A(OFF)
python scripts/policy_pipeline/inject_json.py data/neo4j_load/policies/P012.json   # (또는 non-grant 로더)
POLICY_POI_SORT_BOOST=0 python scripts/sim/run_simulation.py --start <date> --days <14~30> --seed 42   # B(ON)

# M6 채점
python scripts/sim/validate_sangsaeng.py --off <A_run> --on <B_run>
#  → C2(총소비 방향, 필수 판정) + D1(업종 순위, 보조) + C1·D2(탐색적 첨부), SANGSAENG_BACKTEST.md
```

**성공 기준**: **C2(총소비 방향 +) 통과 = 1차 성공.** D1(업종 순위, 가전·가구 상위)이 창발로 함께 나오면 강한 증거로 가산. C1(제외≈0)·D2(소득 재배분)는 게이트가 아니라 탐색적 관찰(§6.3). 무반응(§4.4·§8-7)도 유효한 결과로 기록하며, 사후에 정렬가점을 소급 적용해 "성공"으로 재포장하지 않는다.

### 부록 A. 열린 결정 (M1~M4 진행하며 확정)
- 정확한 표본 크기·관측창 길이(비용 vs 검출력) — 인프라 비용 견적 후 확정.

- Dawn 고지 문구의 정확한 워딩(§4 ⓑ 초안을 M2에서 다듬음) — LLM이 "정책 설명"과 "지시"를 혼동하지 않도록 주의.
