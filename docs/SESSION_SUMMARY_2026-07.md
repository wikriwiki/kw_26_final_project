## 0. 세션의 큰 흐름

```
판매자 에이전트 설계 (v1.0→v1.1)
   └─ "POI 무관 동일 지출" 결함 발견 → 설계 중단 → 소비 알고리즘 우선 수정
소비 알고리즘 재구현 (가격대 도입 → 실측 데이터 계층 → 검증)
   └─ 재구현 자체를 감사(audit) → 순환성·수입 부재 등 리스크 자각
새 미션: 정책 효과 백테스트 (민생회복 소비쿠폰, 과거 실측 대조)
   └─ 사전조사 → 문헌·제도 조사 → 검증 설계 쉬운 설명
   └─ 구현 전제 결함 발견: "쿠폰 가능/불가 POI 구분이 없다" → 구현
   └─ 사용자 지적: "룰 근사 말고 실측 데이터 있는지 찾아봐" → 가맹점 CSV 조인
   └─ 사용자 지적: "소득 부여 계획이 비현실적" → 소지역추정 문헌 기반 v2 재설계
   └─ 최종 미션: "LLM 자율성 vs 통계 일관성" 프롬프트 개선 + 봉투 구조 + preflight
전체 최종 검수 → 커밋 → 푸시
```

**한 문장 요약**: 이 시뮬레이션으로 **민생회복 소비쿠폰(2025)의 실제 효과를 얼마나 정확히
재현하는지 백테스트**하기 위한 전제 조건(쿠폰 사용처 구분·가격 반응·소득 배정·검증 설계)을
갖추는 작업이었다. 판매자 에이전트는 이 과정에서 **보류**되었다.

## 1. 상태 전환 — 무엇이 왜 바뀌었나

### 1-1. 판매자 에이전트 → 보류
설계서(v1.0, v1.1)는 완성했으나(행동 5종·간이 손익 원장·검증 계획), 구현 도중 사용자가
"어렵겠다"고 판단해 **중단**. 문서는 보존(`docs/SELLER_AGENT_DESIGN.md`,
`docs/SELLER_BEHAVIOR_ALGORITHM.md`) — 향후 재개 시 바로 쓸 수 있음.

### 1-2. 미션 전환 — 정책 백테스트
"우리 시뮬이 정책 효과를 잘 예측하는가"를 **과거 실제 정책(민생회복 소비쿠폰)** 으로
입증하는 것이 새 목표. 이유: 판매자 없이도(소비자 에이전트만으로) 검증 가능하고,
프로젝트의 핵심 주장(정책 시뮬레이션 도구로서의 타당성)에 더 직결.

### 1-3. 발견된 전제 결함 2가지 (백테스트를 막고 있던 것)
1. **"어느 가게를 가든 소비 금액이 동일"** — 가격 반응이 없어 정책의 가격 채널이 무의미
2. **"POI에 쿠폰 사용가능 여부가 없다"** — 사용처 제한이 없으면 정책의 업종 DiD(핵심 검증
   방법)가 성립 불가

둘 다 이번 세션에서 해결됨.

## 2. 구현 완료 사항 (코드, 원격 반영됨)

### 2-1. 소비 알고리즘 — POI별 가격 반응 (`907e097`, `98d32c2`)
- `scripts/sim/poi_price.py`: 3계층 가격 결정 — ①카카오 메뉴가(Layer B, 훅만 준비)
  ②**실측 동 건단가**(BDC 카드 데이터에서 비율 역산으로 복원 — EDA 핵심 발견)
  ③fallback(발달지수 순위)
- `scripts/sim/consumption.py`: 장바구니 가격지수로 하루 총지출이 선택한 가게 가격에 반응
  (클램프 [0.8, 1.25]), 하위호환 보장(가격 미지정 시 기존과 동일)
- **핵심 발견**: `dong_consumption.json`의 카드이용금액/건수 비율에서 정규화가 상쇄되어
  **동별 실측 건단가가 복원됨** → 기존 순환성 문제(Huff prior와 동일 변수 사용) 해소

### 2-2. 쿠폰 사용처 판정 (`9be31f1`, `cd3245b`)
- `scripts/sim/coupon_eligibility.py`: 룰 기반 판정 (상호명 브랜드 패턴 + L2 카테고리 제외)
  — 이마트≠이마트24, 스타벅스(직영)≠메가커피(가맹) 등 16케이스 테스트
- `scripts/neo4j_load/09_coupon_eligibility.py`: **실측 가맹점 CSV 우선, 룰은 fallback만**
  (사용자 지적 반영 — "룰 근사보다 실데이터 있으면 그걸 써야")
- `data/coupon/seoul_love_merchants.csv`: 서울사랑상품권 가맹점 140,140건 변환 완료
  (`scripts/prep/convert_merchant_xlsx.py`로 원본 xlsx에서 변환)

### 2-3. 제한 예산 봉투 — 업종 DiD의 구조적 전제 (`3c046f2`, 최종 미션)
가장 중요한 마지막 개선. 기존엔 지원금이 가용자산에 합산되어 **사용불가 업종에도 매출이
새어나가** DiD 대조군이 성립하지 않았음. `apply_consumption_model`에
`restricted_envelopes` 파라미터 추가:
- 필터(사용처/업종/지역)를 통과한 거래에만 지원금이 흐름 (Thaler mental accounting 근거)
- 검증: 사용가능 POI +74,000원 / 사용불가 POI 변화 0원 — DiD 대조군 성립 확인
- **정책 일반화**: 정책의 `poi_restricted`/`target_l1s` 속성에서 필터를 자동 도출 —
  쿠폰 전용 하드코딩이 아니라 어떤 미래 정책에도 적용되는 구조

### 2-4. Windfall 인지 프롬프트 (최종 미션 1·2·3)
- `scripts/sim/dawn_context.py` `_format_policy`: 정책 카드에 "나의 해당 여부 →
  수령/잔여 → 사용조건 → 나에게 의미"를 개인화해서 노출
- **시계열 감쇠**: 어제만 비교하던 것을 경과일 기반으로 — D+0 "오늘 생긴 공돈" →
  D+1~2 "생생함" → D+3~6 "옅어지는 중" → D+7+ "잔액의 일부" (4단계 테스트 완료)
- `scripts/sim/stage1_intent.py`: SYSTEM 프롬프트에 windfall 지출 성향 지침 추가

### 2-5. 정책 사전점검 도구 (최종 미션 5)
- `scripts/sim/policy_preflight.py`: 시뮬 구동 전 정책 JSON 검증 — 스키마, 환경 요구사항
  자동 도출(가맹점 CSV 필요 여부 등), **대상/제외 페르소나가 볼 프롬프트 실제 렌더 미리보기**
- **중립성 원칙 명문화**: "입력 표현·주입 준비만 점검하며 행동 파라미터는 일절 건드리지
  않는다 — 결과를 미리 유도하는 경로 없음" (사용자가 명시적으로 요구한 안전장치)

### 2-6. 가맹점 데이터 분포 분석·시각화 (최종 미션 4)
- `scripts/prep/merchant_stats.py`: 자치구별 가맹점 수·인구당 밀도·업종 분포 통계 +
  `output/sim/report/coupon_merchant_stats.png` (3패널 시각화)
- 사용성 평가: 커버리지 상한 ~26%(140K/540K POI, 룰 fallback 필수), 기준일 2024-03과
  정책 시행 시차(False Negative 가능성 — True 확정 전용 설계로 대응)

### 2-7. 정책 파일 (백테스트용 초안)
- `data/neo4j_load/policies/P010.json` / `P011.json`: 민생회복 소비쿠폰 1·2차
  (근사·한계는 notes에 명시 — 예: 기초수급 가산 미반영, 상위10% tier 근사)
- `scripts/neo4j_load/10_load_grant_policy.py`: 확장 필드(income_grants 등) 포함 로더

## 6. 사용자 피드백 반영 이력 (다음 세션이 반복하지 않도록)

- "판매자보다 소비자 가격 반응부터 고쳐라" → 순서 전환, 옳았음
- "수정이 야기할 문제를 스스로 감사하라" → 순환성·수입부재 등 자가발견, 이후 개선의 근거가 됨
- "룰 근사 말고 실측 데이터 찾아봐" → 가맹점 CSV 조인으로 업그레이드 (룰은 fallback으로 강등)
- "소득 계획이 비현실적, 논문 찾아서 검증까지" → 소지역추정 문헌 기반 v2 + 대량 검증 스위트로 재설계
- "쿠폰에 과적합되지 않게 일반화하라" → 정책 속성 기반 봉투 필터 자동 도출 구조로 해결
- "결과를 미리 유도하는 방식은 절대 안 됨" → preflight에 중립성 원칙 명문화
