# 시간복잡도 최적화 진행 기록

목표: 전체 주요 코드 경로를 검토하고, 동작을 유지하면서 데이터 크기에 따른 계산량을 줄인다. **진행 중이며 전체 목표의 완료 판정은 하지 않았다.**

작업 브랜치는 기존 `codex/gpu-server-backup-20260814`, 비교 기준은 `c684f83098f7585fc8f202805725202b081fcd79`다. 수정은 해당 브랜치의 루트 `scripts/`에 적용했다. `server_backup/gpu_20260814/`는 보존용 스냅샷이므로 수정하지 않았다. 따라서 이 변경이 기존 GPU 서버에서 실행 중인 코드에 배포되었다는 뜻은 아니다. 별도 `feat/report-v2-web-console` 작업 트리의 기존 수정 내용도 보존했다.

## 검증

- 소셜/노출/프레임 차등 테스트 25개 통과. 임의 시드·중복·빈 입력·좌표 누락·비정렬 시각을 포함한다. 기존 알고리즘은 `tests/unit/sim/performance_reference.py`에 비교용으로 고정했다.

- 보고서 새 인덱스 검사 및 기존 analytics/render 검사 46개 통과. 크기가 다른 양수·음수 실수의 합산 순서를 검사했다.
- 전체 `tests/unit` 실행에서는 280 passed / 5 failed / 8 skipped / 5 subtests passed를 확인했다. 이 실행 이후 추가한 페르소나 build 통합 테스트와 보고서 인덱스 테스트는 위 별도 실행으로 검증했다.
- 실패 5개를 수정 전 HEAD의 `git archive` 복사본에서 동일 노드 ID로 다시 실행해 **동일하게 5개 실패**함을 확인했다. 새 최적화의 회귀를 나타내는 실패는 발견되지 않았다. 전체 테스트가 모두 통과했다는 뜻은 아니다.

## 전체 리뷰 현황과 남은 작업

### 후속 진행: 야간 매칭·초기 POI·프레임 검색·조건부 생성

이 절은 아래 초기 검토표의 미완료 항목 중 추가로 처리한 내용이다.

- Night `_softmax_select`: 후보 위치를 유지하는 가중치 트리와 에이전트별 인접 후보 인덱스를 추가했다. 동일 시드의 선택·순서·난수 상태, 경계 근처의 동일 uniform 재사용, underflow 후 최댓값 변경을 검증했다. 32개 테스트 통과. 복잡도는 `O((P+S)log P + RP + BP)`이며 R=최댓값 변경 구간 수, B=부동소수점 경계 재계산 수다. 최악의 경우 기존 O(SP)가 남는다. 자세한 수치 동등성 조건은 [SOFTMAX_COMPATIBILITY.md](SOFTMAX_COMPATIBILITY.md)에 기록했다.
- Night 벤치마크: 2,048/4,096/8,192개 후보에 대해 각각 9.74×/22.26×/33.83×. 최대 입력에서 3.849초→0.114초, 974개 선택 및 난수 상태가 정확히 일치했다. 새 인덱스 생성과 최댓값 변경 시 재생성 비용을 포함했다. [원시 결과](matching_benchmark_20260909.json)
- `07_initial_awareness.py`: 전체 거리 정렬 `O(P log P)`를 안정적인 top-k `O(P log k)`로 바꿨다. 동점 입력 순서를 유지하고 NaN/무한 거리에서는 기존 정렬로 돌아간다. 한 번의 O(P) 거리 계산·유한값 검사는 남는다. 테스트 8개 통과.
- `visualization_3d/derive.py`: 날짜별 프레임 존재 여부는 O(1), 빠진 시각의 가까운 프레임은 O(log H) 조회로 변경했다. 종전에는 각각 전체 F프레임을 순회했다. 실제 시간보다 원래 프레임 인덱스로 동점을 해소하는 규칙, 중복 시각의 마지막 값 우선 규칙을 유지했다. 새 테스트 15개 및 기존 derive 검사 통과.
- `build_conditional.py`: build 단위로 fallback 풀과 `itertools.accumulate` 결과를 재사용한다. 동일한 가중치 누적 순서를 유지하므로 매 추첨은 O(log P), 기존 매번 후보 구성·가중치 누적 O(P)를 없앴다. 사용자 RNG는 기존 경로 유지. 2,000회 추첨·난수 상태 비교와 실제 build 출력 비교 등 12개 테스트 통과.
- 3D JS의 `computeMemoryTotals`는 코드 확인 결과 초기 부팅에서 한 번만 호출된다. 반복 애니메이션 병목이라는 초기 의심은 기각했고, 불필요한 캐시는 추가하지 않았다. 프레임 데이터는 이미 Map으로 초기 인덱싱된다.
- 보고서 snapshot 파일 해시는 무결성 확인을 위해 파일 전체를 읽는 선형 작업이다. 이를 mtime만으로 대체하면 계약이 달라지므로 그대로 유지했다. API 이벤트 집계 역시 파일당 스트리밍 1회 계산이며 캐시를 사용한다. 웹 UI의 날짜별 결제 목록 재필터와 API의 로그 재읽기는 추가 검토 대상으로 남는다.

CPU 함수 개선은 검증했으나 GPU 서버 실행본에는 배포하지 않았다. 전체 코드 리뷰 목표는 계속 진행 중이다.

후속 변경을 모두 포함한 `python -m pytest tests/unit -q --tb=short` 결과는 **357 passed / 5 failed / 8 skipped / 5 subtests passed**다. 실패 노드와 원인은 앞서 수정 전 커밋에서 재현한 동일한 5개이며, 새 실패는 없다.

### 후속 진행: 웹 문답·보고서 기간 판정

- `web/ui/src/lib/agentData.ts`의 전체 소비 답변은 날짜별 `paid.filter(...).reduce(...)`를 한 번의 Map 집계로 변경했다. E개 결제·D개 날짜에 대해 O(DE)→O(E+D). 날짜별 합산 순서와 총액 계산, 음수/0 제외, 날짜 범위 밖 이벤트의 총액 포함 규칙을 그대로 유지한다.
- `node web/ui/tools/test_agent_answer_performance.mjs` 통과(Node 22.20). 실제 TypeScript 함수의 타입만 제거해 실행하며 전체 답변 객체·빈 입력·범위 밖 날짜·큰 실수/작은 실수·입력 불변성을 비교한다. getter로 이벤트 날짜 조회 횟수를 계측해 기간 10일→100일에서 새 구현의 조회량이 증가하지 않음을 확인했다. 이 검사는 브라우저 시각 QA나 end-to-end 실행을 대신하지 않는다.
- `web/ui`에서 lockfile 기준 `npm ci --ignore-scripts --no-audit --no-fund` 후 `npm run build` 성공. TypeScript 및 Vite production build를 검증했다. package/lockfile 변경은 없다.
- 보고서 `build_bundle`의 일자 분류는 기간 목록을 행마다 선형 검색하던 O(D²)를 집합 membership O(D)로 변경했다. 대상업종 집합도 업종마다 생성하지 않고 한 번 재사용한다. analytics/period/render 테스트 46개 통과.
- API의 `parse_run_log`는 마지막 진행 줄과 가장 나중의 헤더를 모두 반영하기 위해 현재 로그 전체를 읽는다. 일반 파일에는 append-only 보장이 없으며 수정·교체·부분 UTF-8 기록도 가능하다. 확인 없이 파일 오프셋만 저장하는 증분 캐시는 추가하지 않았다. 변경 탐지 계약과 동시 기록 검증이 필요한 후속 항목이다.
- BDC `compute_allocation`의 정렬은 출력 순서와 최대 배정 조정 순서를 결정하는 O(N log N) 연산으로 확인했다. 이를 임의 순회로 바꾸지 않았다. `timing_metrics.summarize` 역시 백분위와 기존 정렬 합산 순서를 유지한다. 가격 원천 로딩과 geocode는 이미 캐시/기본키 조회를 사용한다.

이번에는 진입점과 주요 실행 경로를 검토했으며 모든 보조·과거 스크립트까지 완료한 것은 아니다.
