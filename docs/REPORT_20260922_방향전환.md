## 3. 남은 과제 하나의 처방은 프롬프트가 아니다

채점표가 P012 0.49배의 원인과 처방까지 적어 두었다.

```
원인   KDI 는 한 달을 쟀고 우리는 정책 2일을 쟀다. 캐시백은 누적 기전이다
처방   워밍업 3일 + 무정책 7일 + 정책 14~21일로 다시 돌린다
주의   "창이 길어지면 배수가 1 쪽으로 움직일 것"을 먼저 등록하고 돌려라
금지   '더 크게 반응하라'를 프롬프트에 넣는 것
```

## 4. 그런데 그 처방을 그대로 돌리면 엉뚱한 이유로 실패한다

이미 돌아 있던 28일 런(200명, 9/12)을 열어 봤다.

```
총소비   606만 → 215만 (-65%)

잔고 0    7일  2%  ·  14일 20%  ·  21일 42%  ·  28일 67%

마르지 않은 66명만 보면 28일 내내 평평하다
   10-01  29,097원  →  10-28  31,808원
```

**붕괴는 행동이 아니라 지갑이다.** 소득 주입 기전이 저장소에 없다. 초기 잔고는
앵커 × 39일이 전부이고, 실제 소진이 더 빨라 중앙 25.9일 · 최소 9.1일치다.

```
검증된 결과가 전부 짧은 창인 이유   거리두기 n=500 은 12일 < 25.9일
처방을 그대로 돌렸다면              배수가 안 움직였을 것이고,
                                   그것을 "창 길이가 원인이 아니다"로 읽었을 것이다
```

채점표가 그렇게 읽으라고 적어 둔 바로 그 자리에서 틀린 결론을 적을 뻔했다.
([THE_PURSE_RUNS_DRY.md](../experiments/THE_PURSE_RUNS_DRY.md))

```

실제 결제 데이터   v18  1건 10,000 → 1건 9,000   -10.0%

네 라운드를 같은 자로 재면   -10.0 · 정의 안 됨 · -75.0 · +0.0
기여 시민                    2명 · 0명 · 5명 · 3명
```

부호가 아니라 한 자리 수 위의 잡음이다. "두 라운드에서 맞는다"는 두 라운드만
봤기에 할 수 있던 말이다.

**② 정렬 문제는 내 착각이었다.** "실측 음식점이 배달을 포함하는지 모른다"고
적고 그 위에 문서를 하나 세웠는데, 채점표의 DS-1 은 `sector_spend:식사` 이고
그 업종은 배달을 포함한다. **정렬은 처음부터 정해져 있었다.**

**③ 계산 오류.** `+133%` 로 적은 것이 `+33.3%` 다. 192,000/144,000 = 1.333 을
증가율로 옮기며 틀렸다.

**④ 테스트 9개가 수집조차 안 되고 있었다.** `night_intent_llm` 의
