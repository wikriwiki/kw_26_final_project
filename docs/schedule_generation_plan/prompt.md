### 1.1 SYSTEM — 캐시 블록 1 (전역 고정, ~300 토큰)

```
당신은 서울 시민 에이전트의 하루 동선을 설계하는 Daily Planner입니다.
출력은 반드시 주어진 JSON 스키마를 따르며, 자연어 해설을 덧붙이지 않습니다.

[POI 규칙]
- place/poi_id는 [후보 POI] 또는 [고정 장소]에 있는 항목만 사용합니다.
- 후보 밖 장소를 지어내거나, 일반명사("근처 카페")로 기술하지 않습니다.
- 하루 이벤트 수: 평일 5~9개, 주말/공휴일 3~8개.

[이벤트 규칙]
- 첫 이벤트와 마지막 이벤트는 반드시 [고정 장소]의 거주지입니다.
- 평일 + 직장 있음: 09~18시 중 직장 체류가 누적 4시간 이상이어야 합니다.
- 이벤트 간 최소 체류 20분.
- 시간은 24시간제 "HH:MM", 단조 증가.
- 요식업은 식사시간대(11:30~14:00, 18:00~21:00)에 집중.
- 카테고리별 운영시간을 넘는 방문은 금지.

[정책·기억·소식 반영 원칙]
- [인지한 정책]의 수용/저항은 페르소나의 성향·소비분위에 따라 판단.
  · 소비분위 9~10: 쿠폰성 정책에 민감도 낮음.
  · 소비분위 1~4: 쿠폰·지원금 정책에 민감.
- [최근 경험]에서 만족도 ≤ 0.3 POI는 오늘 회피.
- [지인 소식]은 친밀도·성향과 일치할 때만 채택.
- [Running state]의 월누적지출·전일만족도 (정책 수혜 중이면 잔여쿠폰)를 고려해 오늘 동선의 다양성을 유지.

[pinned_poi 사용 규칙]
- [최근 경험]·[지인 소식]에 등장한 POI 중 오늘 직접 방문하고 싶은 항목은 event에 `pinned_poi:"<poi_id>"`로 고정.
  · 단골집 재방문: [최근 경험]의 고만족(≥0.7) POI
  · 지인 추천 실행: [지인 소식]의 pending POI
- 그 외 일상 루틴(출근길 편의점·평범한 점심 등)은 pin하지 말 것. 시스템이 거리순으로 선택.
- `pinned_poi`는 반드시 [최근 경험]/[지인 소식]에 등장한 `poi_id`여야 함.

[purpose / intent 필드]
- 20자 이내의 한국어 명사·짧은 어구 ("점심", "퇴근길 장보기", "지인만남").
```

## 3. POC 시나리오

### 3.1 스코프

| 항목 | 값 |
|---|---|
| 대상 지역 | 강남구 (15개 행정동) |
| 대상 에이전트 | **300명** (행정동×나이대×성별 cell당 1~2명 샘플링) |
| 기간 | **7일** (2026-05-04 월 ~ 2026-05-10 일) |
| 정책 투입 | **D+3 (2026-05-07 목) 에 P001 강남 소비쿠폰 발표** |
| 모델 | Gemma-4-26B-A4B, Qwen2.5-7B, EXAONE-3.5-7.8B 3종 병렬 비교 |
| GPU | 단일 A100 80GB (공유) |
| 예상 벽시계 | 모델별 4~8시간 × 3 = 1일 내 완료 |

### 3.2 정책 P001 정의

```yaml
policy_id: P001
name: "강남구 소비쿠폰 10만원"
```

### 3.3 KPI 체크리스트

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| JSON 스키마 검증 통과율 | **≥ 95%** | `validator.py` 리포트 |
| 후보 밖 POI 환각율 | **0%** | `poi_id ∉ fixed ∪ candidates` 카운트 |
| 운영시간 위반율 | **≤ 5%** | category_hours와 비교 |
| 이벤트 간 20분 위반율 | **≤ 2%** | time diff 체크 |
| 평일 직장 체류 ≥ 4h 준수율 | **≥ 95%** (직장 보유 에이전트) | sum(workplace stay) |
| **정책 인지→행동 변화 감지** | **D+3 이후 식사/카페 방문률 상승** | D+0~D+2 vs D+4~D+6 비교 |
| 부유층(9~10분위) 쿠폰 채택률 | **< 전체 평균** | source_context.policy_applied 분포 |
| 소셜 전파 효과 | **D+5까지 awareness ≥ 0.3 에이전트 비율 60% 이상** | policy_context 주입율 추이 |

### 3.4 성공/실패 기준

- **성공**: 상위 4개 지표 목표 충족 + "D+3 정책 인지→행동 변화"가 통계적으로 유의 (p < 0.05, 이항검정)
- **보류**: 환각율은 0이나 정책 반응이 미미 → 프롬프트 튜닝 후 재POC
- **실패**: 환각율 > 0 또는 스키마 통과율 < 90% → 모델 교체 또는 후보 포맷 재설계

## 5. 프롬프트 튜닝 체크리스트 (POC 후)

1. System 블록의 "이벤트 규칙" 순서 → 모델이 가장 자주 어기는 규칙을 맨 앞으로
2. `후보 POI` 카테고리 헤더 표기 → `[식사/거주]` vs `# 식사 (거주근처)` 중 토큰 효율 확인
3. `정책·소식·기억 반영 원칙` 섹션 → 부유층 민감도 문구가 과하게 작동하면 완화
4. `purpose` 필드 예시 추가 여부 → 지나치게 추상화되면 예시 5개 삽입
5. 변동부 `running_state` JSON 포맷 → 키 한국어 vs 영문 토큰 비교, 쿠폰 생략 여부 제어
