# 메가존클라우드 제공 서버 지속성 점검

점검일: 2026-09-19 KST

대상: 현재 EXAONE 4.5 시뮬레이션 서버

점검 중 실제 시뮬레이션은 시작하지 않았다.

## 결론

- SSH 연결이 끊겨도 `nohup`과 `setsid`로 실행한 프로세스는 계속 실행된다. 별도
  SSH 세션에서 무해한 지연 쓰기 프로세스를 띄우고 최초 연결을 닫은 뒤, 다시 접속해
  `/data`의 완료 파일을 확인했다.
- `/data`는 루트 볼륨과 분리된 1 TB 블록 장치(`/dev/sdb1` → LVM → ext4)이며
  `/etc/fstab`에 등록돼 있다. 점검 시 약 892 GB가 비어 있었다.
- 사용자 확인: 현재 서버는 메가존클라우드에서 제공했다. 이전 답변에서 적용한 NHN
  GPU Live의 8시간 유휴 회수 규칙과 스토리지 폴더 계약은 이 서버에 적용된다는 근거가
  없으므로 철회한다. 호스트 내부 마운트만으로 제공사의 데이터 보존 계약을 확정할 수 없다.
- 인수인계에 적힌 회수 예정일은 2026-11-05 17:00이다. 이는 인수인계 정보이며
  제공사의 최신 계약을 별도로 확인한 값은 아니다. 재부팅·반납·회수 시 보존 여부도
  메가존클라우드 제공 조건을 기준으로 확인해야 한다.

## 현재 저장과 복구 특성

`run_simulation.py`는 에이전트 결과를 JSONL에 즉시 flush하고, 완료 에이전트 목록을
500명마다 체크포인트로 쓴다. 하루가 끝나면 summary를 원자적으로 교체한다.
`BACKUP_DIR`가 설정되면 하루별 State와 체크포인트·메트릭·타이밍 파일을 임시 파일에
쓴 뒤 원자적으로 교체하고 SHA-256 manifest를 남긴다.

한계도 있다.

- 에이전트 하루치의 Plan, Memory, State가 하나의 원자 트랜잭션으로 묶여 있지 않다.
  에이전트 처리 도중 프로세스가 죽으면 Neo4j에 일부만 기록된 agent-day가 생길 수 있다.
- Neo4j와 SGLang은 현재 systemd 서비스가 아니다. SSH 단절에는 살아남지만 서버가
  재부팅되면 `/data/setup_neo4j.sh`와 `/data/start_sglang.sh`로 다시 시작해야 한다.
  2026-09-20 추론 비교용 실행은 `/data/start_sglang_reasoning.sh`를 사용한다.
  이 스크립트는 같은 EXAONE-4.5-33B-AWQ에 `--reasoning-parser qwen3`만 추가하고
  별도 로그를 남긴다. 원본 시작 스크립트는 보존했다.
- 서버의 `/data/dumps/neo4j.dump`는 2026-09-11 기준 베이스 덤프다. 이를 로컬 Drive의
  `output/neo4j_backup_20260911_server/neo4j.dump`로 복제했다. 원본과 사본은 모두
  1,009,225,694바이트이며 SHA-256
  `4452e67b6631da264e28ad23c200d1f1d2393480015811df9726ba235127d3af`로 일치한다.
  이 덤프는 Git에는 넣지 않고 Drive에 보관한다. 9월 11일 이후의 실험 진행 상태를
  담은 덤프는 아니므로 결과 JSON과 하루 백업은 별도로 보존해야 한다.

## 이번에 적용한 안전장치

- `/data/start_stage8_safe.sh`를 만들었다. 중복 PID를 확인하고 `nohup setsid`로 Stage 8을
  SSH 세션 밖에서 실행하며, 고유 로그와 PID 파일을 남긴다. 저장소 사본은
  `scripts/exp001/start_stage8_safe.sh`이다.
- `/data/stage8.sh`가 각 런에 별도 `BACKUP_DIR`를 지정하도록 했다. 하루가 끝날 때마다
  `/data/stage8/<태그>_backup/`에 원자 백업과 manifest가 생긴다.
- 동일 태그의 미완료 출력 디렉터리가 있으면 삭제하지 않고
  `<태그>_interrupted_<시각>/`으로 이동한 뒤 깨끗하게 재시작하도록 했다.
- 완료·실패 에이전트 체크포인트도 임시 파일을 거쳐 원자적으로 교체하도록 바꿨다.
- 서버에만 있던 Stage 8 재사용 결과 세 파일을
  `docs/experiment_evidence/stage8_reused/`로 복제했다.

## 장애별 영향

| 상황 | 실행 | 데이터 |
|---|---|---|
| 로컬 SSH·인터넷 단절 | 안전 런처 사용 시 계속 실행 | 손실 없음 |
| 터미널에서 `bash /data/stage8.sh` 직접 실행 | SIGHUP으로 중단될 수 있음 | 완료분은 남지만 수동 검증 필요 |
| Python 프로세스 오류 | 중단 | JSONL·체크포인트·Neo4j 완료분은 남음. 부분 agent-day 가능 |
| 서버 재부팅 | 중단, 서비스 자동 복구 안 됨 | `/data`가 다시 마운트되면 파일과 Neo4j 저장소는 남음 |
| 제공사의 서버 반납·회수 | 중단 | 제공 계약 확인 필요. `/data` 보존을 보장할 근거 없음 |
| `/data` 볼륨 삭제·프로젝트 만료·스토리지 장애 | 중단 | 서버 내부 백업도 함께 손실. 외부 복제만 보호 가능 |

## 실행 전 필수 확인

**2026-09-20 현재 검증에는 아래의 역사적 Stage 8 절차를 사용하지 않는다.**
검증 파일럿은 `/data/validation_v3/repo`의 독립 코드 사본에서 실행하며,
`/data/validation_v3/pilot_registered`에 고정 입력·해시 manifest와 원문 결과를 보관한다.
입력 준비 때 Neo4j를 읽었고 실행 중에는 DB 쓰기나 초기화를 하지 않는다.
`nohup setsid`로 SSH 세션과 분리했고, 응답마다 JSONL flush 및 fsync를 수행한다.
기존 결과 파일이 있으면 자동 재시작·덮어쓰기를 거부한다. 중단 시 완료 응답은
보존하되, 그 자체가 미완료 호출의 안전한 자동 재개를 구현한 것은 아니다.
고정 입력 및 manifest는 로컬 `output/validation_v3/pilot_registered/`에도 복제했다.
서버 밖 복제는 이 경로에 실제로 복사한 시점까지를 보호하며, Drive의 클라우드 동기화
완료나 제공사의 서버 회수 후 보존을 이 검사만으로 보장하지 않는다.

아래 항목은 이전 Stage 8 운영 기록이다. 후속 본 검증은
`docs/VALIDATION_ROLLOUT_DESIGN.md`의 격리·완전성·복구 조건을 충족한 런처를 사용한다.

1. 채점기 세대를 결정하고 서버 코드를 고정한다. 구 채점 결과와 새 채점 결과를 한 표에
   섞지 않는다.
2. 메가존클라우드 제공 조건에서 서버·볼륨의 보존 및 회수 일정을 확인한다.
3. Neo4j와 SGLang의 상태와 모델 ID를 확인한다.
4. Stage 8은 `/data/start_stage8_safe.sh v5`로만 시작한다.
5. 하루 백업 manifest가 생길 때마다 로컬 또는 별도 스토리지로 복제한다.

중단 후에는 Stage 8을 즉시 다시 실행하지 않는다. 프로세스, 마지막 로그, Neo4j 상태,
checkpoint와 backup manifest를 먼저 확인한다. 부분 agent-day가 없다고 보장할 수 없으면
보존된 미완료 산출물은 진단용으로 두고 해당 정책 런을 깨끗하게 다시 시작한다.
