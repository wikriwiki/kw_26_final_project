```
                              n     off      on      변화    쌍별                 양측 p
표시된 이벤트(계기:policy)     70  51,400 -> 51,157  -0.5%  늘32 : 줄29 : 동점 9   0.798

```

**표시된 쪽이 안 움직인다.** 기각.

대조군도 안 움직인 것은 좋은 신호다 — 프롬프트가 길어져 생기는 잡음은 없었다.
즉 "아무 효과도 없다" 이지 "재는 눈이 흐리다" 가 아니다.

## 처음 표가 "표본 없음" 이었다 — 두 가지에 걸렸다

```
1  policy_spend: {"P009": 5000}  중괄호가 중첩돼 정규식이 pick 을 통째로 못 잡았다
2  pick 의 order 가 **외출 이벤트만 0부터** 센다.
   프롬프트 머리글의 "### 이벤트 3"(Stage1 인덱스)과 번호가 다르다 —
   실제 응답에서 order 0 이 점심(Stage1 인덱스 1)이었다
```

JSON 을 제대로 파싱하고 번호를 옮겨 **같은 응답으로 다시 셌다**(새 호출 0).

## 이 탐침의 한계를 분명히 적는다 — 후보 1 에도 해당한다

production 의 Stage2 는 **strict JSON schema** 로 부른다.

```
stage2_poi.py:785  expected_orders = [i for i, ev in enumerate(stage1.events) ...]
                   -> s2_schema -> response_format 으로 order 를 강제한다
```

**내 Stage2 탐침 둘(후보 1·3)은 그 스키마 없이 불렀다.** 그래서 모델이 자기
번호를 썼고(위 2번), 생성 경로가 production 과 완전히 같지는 않다.
금액 자체에 거는 제약은 아니므로 비교는 성립하지만, **"production 과 동일
조건" 이라고는 말할 수 없다.** 다음에 Stage2 를 재면 스키마를 함께 건다.

## 세 번의 기각이 한 그림으로 모인다

```
후보 1  문턱 줄  -> Stage2 금액    p=0.678   무효
후보 3  trigger -> Stage2 금액    p=0.798   무효
후보 2  빈자리 줄 -> Stage1 이벤트  p=1.000   무효 (복제)
```

**Stage2 의 `actual_spent` 는 동네×업종 평균단가에 묶여 있고 정책 맥락에
반응하지 않는다.** 문턱을 줘도, 계기를 줘도 안 움직인다.

그러면 실제 런의 **+9.76%** 는 어디서 오나. 남는 경로는 하나다.

```
정책 -> Stage1 이 **다른 이벤트**를 만든다 (가전 구매 등)
     -> Stage2 가 **그 업종의 평균단가**로 값을 매긴다 (가전 56,500 vs 식사 13,500)
     -> 계획액이 오른다
```

이벤트 **수**는 그대로인데(11.5 → 11.5) 금액이 오른 것이 이것으로 설명된다.
Stage2 는 정책을 모르는 **업종 기반 가격기**이고, 정책은 Stage1 의 업종 선택을
통해서만 금액에 닿는다.

## 그래서 프롬프트로 더 밀지 않는다

Stage1 은 이미 반응한다(+9.76%, p=0.0015). 그것을 더 키우려는 시도가 세 번
실패했고, 더 세게 미는 문장은 **사용자가 금지한 유도**에 가까워진다.

> "프롬프트 자체에는 정책 결과에 대한 노골적인 방향이나 특정 수치를 작성하면서
> 유도하게해서는 안돼"

**남은 정당한 지렛대는 회계다.** 이미 있는 +9.76% 가 총액에 닿지 못하고
`max(앵커,계획)` 에서 4분의 3이 버려지는 것을 고치는 일은 유도가 아니라
새는 것을 막는 일이다(`../error_budget/diagnosis_05.md`).
