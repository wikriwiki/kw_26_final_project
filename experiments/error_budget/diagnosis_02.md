# 정책의 핵심 경로가 상수로 막혀 있다 — 오차 77%의 회계적 원인

**2026-09-24 03:30** · 런 자료 2,814건(p013_ruler arm A) · 코드 `consumption.py`

## 소비가 만들어지는 3층

런 자료의 중앙값으로 그리면 이렇다.

```
① 앵커      총액 = spend_today(p, daily_wd) x basket_idx        95,789원
              p = Stage1 의 daily_propensity (0~1)
② 가맹 몫    그중 ELIGIBLE_SHARE_SEOUL = 0.2535 만 POI 로 간다   25,794원
              나머지 75%는 POI 원장에 들어오지 않는다
③ 업종 분할  그 25% 안에서 적립/제외를 가른다                     ← 지표가 재는 곳
```

## 세 층이 각각 상수다

**① `p` 가 상수에 가깝다.** 계획 2,810건에서 서로 다른 값이 **19개**뿐이다.

```
0.68  54.4%      0.65  21.1%      0.58  7.9%      0.62  7.0%
상위 넷이 90.4% · 범위 0.42~0.86 (0~1 의 중앙 44%만 씀)
```

프롬프트 예시값은 0.72 이고, 두 번째로 많은 0.65 는 프롬프트의 `sat 0.65` 와
같은 수다. **스칼라가 상황이 아니라 프롬프트 안의 숫자에 붙어 있다.**

그리고 **문턱에 반응하지 않는다.** 문턱까지 남은 거리만 바꾼 격자(120 호출,
2026-09-22)에서 양 끝 차이가 **0.005(0.8%)** 였고 단조도 아니었다.

**② 가맹 몫이 전원 동일하다.** 2,836건 전부 0.75 다(분포에 값이 하나뿐).
코드 주석은 "몫은 Stage1 에서 본인이 판단한다" 고 적혀 있으나, LLM 판단은
"계층 구분 없이 0.2 근처로 균일해 정보가 없었다"는 측정 뒤 폐기되고
서울시 소상공인 자료의 상수 0.2535 로 대체됐다.

**③ 앵커를 계획이 넘는 일이 거의 없다.** `personal_total = max(앵커, 계획)`
인데 계획액이 앵커의 **56%**(중앙)다.

```
앵커 넘은 사람   0.3% · 0.4% · 0.7% · 1.4%   (나흘)
```

## 그래서 정책의 핵심 경로가 봉쇄된다

**상생소비지원금의 기전은 "적립업종(=동네 가맹점)에서 쓰면 캐시백" 이다.**
즉 이 정책은 **②의 몫을 올리는 정책**이다. 그런데 ②가 상수다.

```
파이 크기(25.35%)가 고정이므로
적립업종이 오르는 유일한 길은 **제외업종에서 빼 오는 것**이다
```

그것이 관측된 모양이다 — 적립 +1.90% · 제외 −13.90%, **합이 거의 0**.
실측은 둘 다 올랐다(+20.82% · +2.85%, 몫 가중 총액 **+7.67%**).
우리는 총액을 **−9.67%** 로 줄였다. **방향이 반대이고, 구조가 그것을 강제한다.**

**P012-2 의 관측 23명도 여기서 나온다.** 제외업종(대형마트·백화점·온라인)
지출은 ②에서 이미 걷혀 나갔다. ③에 남은 제외업종은 잔여물이다. 표본이 작은
것이 아니라 **구조가 그 돈을 먼저 치웠다.**

**35.67%p(77%)가 ①②에서 나온다.** 프롬프트 문장으로 닫히는 자리가 아니다.
두 번 확인했다 — 범위의 산술을 더한 후보는 부호 검정에서 갈리지 않았고
(p=0.549), 문턱 격자는 숫자를 바꿔도 성향이 0.8% 움직였다.

## 고칠 자리 — 순환을 피하는 길은 하나다

```
가  ② 를 **에이전트의 계획에서 도출한다**
    에이전트는 이미 POI 를 고른다. 그중 적격 매장이 몇이고 얼마인지는
    계획에서 바로 나온다. 상수 0.2535 로 덮어쓰지 말고 **고른 POI 로 계산**한다.
    · 순환이 아니다 — 정책 파라미터나 측정 공식이 아니라 에이전트 자신의 선택이다
    · 이벤트 채널은 반응한다 — 문턱 격자에서 적립 이벤트가 3.75~4.67 로 24% 움직였다
      지금은 그 반응이 ②의 상수에 눌려 총액에 반영되지 않는다
    · 상수를 도입한 이유(BDC 업종 분류가 사용처 판정과 어긋남)는 **이미 해소됐다** —
      POI 단위 적격 판정(is_coupon_eligible · sangsaeng_eligible)이 지금 있다

나  ① 을 정책에 반응하게 — 프롬프트로는 안 된다(격자). 출력 축 추가는
    JSON 계약 변경이라 골든 스냅샷과 관문 라인 전체가 흔들린다. 뒤로 미룬다

다  ③ 만 손대기 — 파이가 고정인 채 분할만 바꾸는 것이므로 제로섬을 못 벗어난다
```

**가 를 다음 실험으로 올린다.** 다만 `EXP_ELIGIBLE_SHARE` 가 환경변수이므로,
코드를 고치기 전에 **민감도부터 잰다** — 몫을 0.2535 에서 올리면 오차가 어느
방향으로 가는지. 그것이 ②가 정말 원인인지 가르는 값싼 시험이다.

> 이 문서가 적는 것은 여기까지다. **총액·가맹몫·계획이 모두 상수에 가깝고,
> 상생소비지원금은 가맹몫을 올리는 정책인데 그 몫이 상수 0.2535 로 고정돼
> 있어 정책의 핵심 경로가 회계적으로 봉쇄돼 있다는 것. 그리고 그 상수를
> 도입한 이유는 이미 해소됐다는 것.**
