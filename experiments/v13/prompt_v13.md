# 실험 v13 — 프롬프트 대신 게이트의 판정을 돌려준다

**날짜 2026-09-21** · **상태** 완료 — **실패, 그러나 처음으로 방향이 맞았다**

---

## 프롬프트 경로는 끝났다

같은 원본·같은 seed·같은 잣대로 세 축을 차례로 시험했다.

```
                        막힌 칸 / 96      평균
v25  (대조)              46 · 47 · 42 · 44   44.8
v32  어구를 고침          46 · 45 · 46 · 47   46.0
v11  자리를 옮김          47 · 42 · 45 · 44   44.5
v33  순서에 넣음          46 · 42 · 45 · 44   44.25
```

**넷이 전부 같은 자리다.** 그리고 모델은 **이미 이해하고 있다** —
재고 0인 48칸 중 22칸의 사고에 `groceries` 가, 26칸에 `delivery` 가 나오고
빈 사고는 0건이다. **아는데 어떻게 말해도 계획에 반영되지 않는다.**

## 그래서 말을 바꾸는 대신 결과를 알려 준다

게이트는 **무엇이 몇 개 모자란지 정확히 안다.**

```
{"event_id": "event:3", "time": "16:00", "resource": "meal_stock",
 "maximum_available": 0, "required": 1}
```

지금까지 이 판정은 **거부에만** 썼다. 이것을 모델에게 돌려주고 같은 하루를
다시 짜게 한다.

### 저장소에 이미 있던 것, 그리고 빠져 있던 것

`prepare_action_repair.py` · `action_repair_feedback.py` 가 있었고 규율도 좋다 —
사실만 돌려주고, **"평가 통과를 위해 구매·외출을 일괄 삭제하지 않는다"**,
**"정책의 성공·소비 변화 방향·금액을 목표로 수정하지 않는다"** 를 이미 적어 두었다.

그런데 **계약 실패(`eligible=False`)만 골라냈다.** 게이트가 막은 칸은
**계약이 유효하다** — 형식도 시각도 다 맞고 물리적으로만 불가능하다.
그래서 수정 경로가 **자기가 만들어진 이유인 실패를 못 보고 있었다.**

이번에 게이트 판정을 되먹임에 실었다. 더한 지시는 한 줄이다.

```
자원이 모자란 항목은 그 자원을 확보하는 일을 함께 넣거나,
자원이 필요 없는 다른 방법으로 바꾼다.
```

**두 갈래를 다 열어 둔다.** 장보기·배달·외식·포장·거르기가 전부 만족한다.
무엇을 사라고도, 어디로 가라고도 하지 않는다(검사로 막음).

---

## 사전등록 — 이 라운드는 형식이 다르다

**수정본은 첫 시도가 아니다.** 그래서 원본인 척 쓰면 안 되고, 전부 남긴다.

| 남기는 것 | 왜 |
|---|---|
| 첫 계획 (`plans/responses.jsonl`) | 수정 전 상태 |
| 게이트 판정 (`psrc_*.json`) | 무엇이 모자랐나 |
| 되먹임 묶음 (`repair_parents`) | 모델에게 정확히 무엇을 줬나 |
| 수정 계획 (`repair/responses.jsonl`) | 수정 후 |
| 두 번째 게이트 판정 | 고쳐졌나 |

`prepare_action_repair` 가 원래 `original_attempt_key` · `original_raw_sha256` ·
`feedback` 을 `repair_parents` 에 남기게 돼 있다. 그대로 쓴다.

### 설계

| | 내용 |
|---|---|
| 첫 계획 | **v12 의 v33 팔 그대로 쓴다** (seed 66001~4, 384칸). 다시 돌리지 않는다 |
| 수정 대상 | **게이트가 막은 칸만.** 통과한 칸은 재생성하지 않는다 |
| 프롬프트 | v25 계열 그대로. 되먹임 블록만 입력에 덧붙는다 |

### 판정 — 주 지표는 수정 뒤 막힌 칸

| | 기준 |
|---|---|
| **성공** | 수정 뒤 막힌 칸이 **전체의 10 이하** (96칸 기준) |
| **부분** | 11 ~ 30 |
| **실패** | 31 초과 — 틀렸다고 알려 줘도 못 고친다 |

**성공을 취소하는 조건**

| | |
|---|---|
| 일괄 삭제 | 구매·외출을 통째로 지워 통과하면 **회피**다. 수정 전후 구매 건수를 함께 본다 |
| 계약 파손 | 수정본이 계약을 깨뜨리면 실패다 |
| 다른 칸 오염 | 막히지 않은 칸을 건드렸으면 프로토콜 위반이다 |

### 기록만 하는 것

무엇으로 풀었는지(장보기 · 배달 · 포장 · 매장 · 집밥 감소) 센다. **점수로 쓰지 않는다.**

### 이 실험이 답하지 않는 것

- **최적 프롬프트** — 이 라운드는 프롬프트를 고르지 않는다. 계획이 물리적으로
  가능해지는 것이 먼저다
- 수정된 계획이 옳은 계획이라는 것 — 아니다. **가능해질 뿐이다**
- 되먹임 없이도 되는가 — v10·v11·v12 가 그 답이 아니오임을 이미 보였다

## 결과 — 판정은 실패. 그런데 처음으로 모델이 옳은 쪽으로 움직였다

수정 계획 **46/46 유효**, 계약 통과, 사후 보정 0.

```
수정 뒤 게이트   검사 46 · 불가능 44
```

사전등록한 선("10 이하 성공 / 31 초과 실패")으로 **실패**다.

### 그런데 무엇이 바뀌었는지 보면 다르다

```
수정 대상 46칸 · 계획이 바뀐 칸 25 · 그대로 21

바뀐 방향 (수정후 − 수정전, 건수)
  home_meal        −9     집밥을 줄이고
  home_delivery    +9     배달로 바꿨다
  groceries        +3     장도 봤다
  provided_laundry +8
  home_chores      −7
```

**여덟 라운드 만에 처음으로 모델이 옳은 방향으로 움직였다.**
`home_meal` 을 `home_delivery` 로 바꾸는 것 — v12 까지 아무 지시로도 시키지
못했던 바로 그 동작이다. 게이트 판정을 돌려주자 25칸에서 그렇게 했다.

### 왜 그래도 막히나 — 절반만 고친다

```
수정 뒤에도 막힌 칸의 부족 자원
  meal_stock      69건  (44칸에 걸쳐 · 칸당 약 1.6건)
  detergent_dose   3건
```

재고 0에 끼니가 **둘**인데 **한 끼만 고친다.** 그리고 `provided_laundry` 가
+8 늘면서 **세탁을 3칸에서 새로 깨뜨렸다** — 한쪽을 고치다 다른 쪽을 부쉈다.

### 정리하면

| | |
|---|---|
| **프롬프트로는** | 어구·자리·순서 셋 다 무효 (v10·v11·v12) |
| **되먹임으로는** | 방향은 맞다. 크기가 모자라고 새 위반이 생긴다 |

**되먹임이 프롬프트보다 낫다는 것은 확인됐다.** 다만 한 번으로는 부족하다.

### 다음 — 반복하면 수렴하는가 (v14)

같은 프로토콜을 **아직 막힌 칸에만** 한 번 더 돌린다. 한 바퀴가 4분이다.

수렴하면 되먹임 루프가 답이고, 두 번째에도 절반만 고치면
**모델이 한 번에 하나씩만 고치는 것**이므로 부족분 수만큼 돌려야 한다는 뜻이다.
그때는 루프를 몇 바퀴 도는지가 이 시뮬레이터의 비용이 된다.
