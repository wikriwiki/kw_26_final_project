# v5 가 실제로 틀리는 것 — 셋뿐이고, 셋 다 형식이다

**2026-09-22 10:30** · `/data/validation_v3/pilot_registered/responses.jsonl` · GPU 불필요

---

## 새 런 없이 알 수 있었다

v5 의 원문 계약 통과율은 128/192 (66.7%) 이고 사전등록 관문은 95% 다. 그 격차를
메우려면 무엇이 틀리는지 알아야 하는데, **384개 응답 원문이 이미 저장돼 있었다.**

```
v5 위반 (이벤트 단위)
  anchor_category   25응답
  explanation       23응답
  zone              19응답
  time               8응답
  category           5응답
```

이 라벨로는 고칠 수 없다. 원문을 열어 보면 셋으로 모인다.

## ① 집·직장에서 먹은 끼니 — 31건

```
residence + category="식사"   23건
workplace + category="식사"    8건

{"time":"07:15","anchor":"residence","category":"식사","sub_category":"한식","intent":"아침 식사"}
```

**프롬프트는 이미 세 번 금지하고 있다.**

```
31행  anchor='residence'일 때 category='집' (수면·휴식·재택·집안일만)
43행  "residence": 집 안에서만 일어나는 활동. category는 '집'만.
49행  절대 금지: anchor='residence' + category='편의점/식사/카페/한식/...' 같은 조합
```

세 번 말했는데 서른한 번 어긴다. **강조를 더 하는 것은 답이 아니다.**
같은 프롬프트가 열 줄 위에서 반대로 말하고 있기 때문이다.

```
39행  **식사** = 식당·한식·양식·중식·일식·분식 등 끼니. 음주 동반이라도 끼니가 주목적이면 식사.
```

**끼니는 식사다. 그런데 집에서 먹은 끼니는 집이다.** 모델은 이 모순을 자연스러운
쪽으로 푼다 — 아침을 먹었으니 식사라고 적는다.

> 고칠 것은 강조가 아니라 **정의**다. 이 목록은 활동의 종류가 아니라
> **가게에서 돈을 쓰는 업종**이다. 집에서 차려 먹은 끼니는 가게 방문이 아니다.

## ② 출퇴근 — 24건

```
zone:xxxxxxxx + category="직장"   24건

그 이벤트의 intent
  13  출근        2  업무 회의
   4  퇴근        나머지  업무·업무 집중·오전 업무 회의 …
```

어휘 열넷 중에 **이동·통근이 없다.** 출근은 집에서 직장으로 가는 일이라 집도
직장도 아니고, 가게에 들르는 것도 아니다. 모델은 빈자리를 zone 앵커 + 직장 업종으로
메운다. **그럴듯한 발명이고, 계약은 그것을 거부한다.**

프롬프트는 이 경우를 말하지 않는다. 47행이 오히려 헷갈리게 만든다.

```
47행  직장 동 근처 외출(예: 점심 식당·퇴근길 카페) → zone:<work_dong_code>
```

"직장 동" 과 "zone" 이 한 줄에 붙어 있다.

## ③ `"reason"` — 23건

```
빠진 것으로 집계된 reasoning 23건의 정체

  21건  키 이름이 "reasoning" 이 아니라 "reason"
   2건  "reasonning"

{"time":"23:00","anchor":"residence","category":"집","intent":"취침",
 "reason":"평일 취침 시간은 대체로 23시 전후. 재택 생활로 인해 늦은 취침은 피하고…",
 "trigger":"none"}
```

**내용은 멀쩡히 들어 있다. 철자만 틀렸다.** 그리고 한 응답에 정확히 하나씩,
스물세 응답에서, **전부 residence 에서** 났다.

```
위치   마지막 이벤트 10건 · 나머지도 전부 뒤쪽 (9/10, 11/13, 14/15 …)
intent 취침 9 · 귀가 3 · 귀가 및 휴식 3 · 취침 준비 2 …
```

하루를 다 적고 마지막 한 줄을 닫으면서 키 이름이 짧아진다.
zone 이벤트 714개와 workplace 이벤트 263개에서는 **한 번도 나지 않았다.**

## ④ time 빈 문자열 — 3건 · ⑤ L1 자리에 하위 업종 — 3건

```
time 위반 8건의 정체
  4  간격 15분   ← 셋이 출근·퇴근 이벤트다. ②가 없애면 함께 사라진다
  3  빈 문자열 ''
  1  간격 10분

category 위반 5건
  2  '약국'   (→ 건강)
  2  '교통'   ← 출퇴근이다. ②가 덮는다
  1  '레저'   (→ 여가)
```

어휘표는 열넷을 나열하지만 **그 밖의 이름을 만났을 때 어떻게 하라는 말이 없다.**
그리고 "반드시 포함" 목록에 `time` 이 없다.

## 상한 — 저장된 원문으로 계산한다

고침이 완벽히 들었다고 보고 384개 응답을 다시 채점했다.

```
  v5                          128/192   66.7%
  ①②③                        183/192   95.3%
  ①②③ + ④ time · ⑤ 업종 매핑   189/192   98.4%
  사전등록 관문                 183/192   95.0%
```

**①②③ 만으로는 관문 경계에 딱 걸린다.** 그래서 ④⑤ 를 넣는다.

**이것은 상한이지 예측이 아니다.** 실제 준수율은 이보다 낮다 — 규칙을 적는다고
모델이 다 지키지는 않는다는 것이 이 문서의 출발점이었다.

## 일부러 안 고친 것

```
남은 6건   시간 간격 4 · 목록 밖 zone 코드 2
```

둘 다 **프롬프트가 이미 말하고 있다.**

```
- 이벤트 간 최소 체류 20분.
zone anchor의 dong_code는 ... 위 'zone 후보' 목록의 코드만 그대로 복사할 것.
```

세 번 말해도 서른한 번 어기는 것을 봤다. 같은 말을 네 번째로 하지 않는다.
**남겨 두고, 다음 런에서 그 여섯이 그대로 남는지 본다.**

> 목록 밖 코드 4건 중 3건이 `zone:11680103`·`zone:11680111` 이다 —
> **프롬프트 예시에 박혀 있는 코드다.** 예시를 지우면 v10 이 되므로 지우지 않는다.
> 이 자리는 다음 라운드의 물음으로 남긴다.

## 그리고 셋 다 정책과 무관하다

```
①  업종 어휘의 정의를 고친다 — 가게 방문인가 아닌가
②  어휘에 없는 경우(이동)를 명시한다
③  필드 이름을 한 번 더 못 박는다
```

**방향도 수치도 없다.** 어느 정책의 결과와도 무관하고, 정답지를 보지 않고도
원문만으로 찾은 것이다.

> v10 은 형식 예시를 없애서 7.3% 로 무너졌다. 이 셋은 반대 방향이다 —
> **형식을 더 정확하게 만든다.** 문장을 더하지 않고 모순을 없애고 빈자리를 메운다.
