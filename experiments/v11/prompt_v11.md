# 실험 v11 — 같은 요구를 같은 자리에 적는다

**날짜 2026-09-21** · **상태** 완료 — **실패. 자리도 지렛대가 아니었다**
**대조군은 v10 의 v25 팔** (같은 프롬프트 · 같은 seed · 원본만 다름)

---

## v10 이 남긴 것

시스템 프롬프트를 고쳐도 아무 일이 없었다.

```
막힌 칸 / 96        66001  66002  66003  66004   평균
v25 (현직)            46     47     42     44    44.8
v32 (범위 명시)        46     45     46     47    46.0
```

"배치하는 **모든** 활동에 대해"라고 못 박아도 모델은 자기가 고른 `home_meal` 에
자원 검사를 걸지 않는다.

## 찾은 비대칭

두 요구가 **서로 다른 자리에** 적혀 있었다.

```
세탁   "실험 가정: provided_laundry는 집에서 세탁 1회를 하는 활동이며,
        실제 시작 전에 세제 1회분이 있어야 한다."     ← JSON 앞, 산문 한 줄

끼니   meal_stock · activity_consumption · assumptions   ← JSON 필드 안에만
```

**모델은 문장으로 읽을 수 있는 요구는 지키고, 필드에서 추론해야 하는 요구는 무시한다.**
세제는 재고 0이면 온라인으로 주문한다. 끼니는 재고 0이어도 집밥을 두 끼 계획한다.

`add_meal_need.py` 가 자원·소비·견적·필요는 채우고 **증거 줄만 만들지 않았다.**
세탁과 같은 구조라고 했는데 한 조각이 빠져 있었다.

## 무엇을 바꾸나 — 문장 하나, 같은 형식

```
실험 가정: home_meal은 집에서 한 끼를 드는 활동이며,
          실제 시작 전에 집에 있는 식재료 한 끼분이 있어야 한다.
```

세탁 문장과 **구조가 같다**. 들어가는 자리도 같다(JSON 앞).

**어디서 먹으라고도, 무엇을 사라고도 하지 않는다.** 검사로 막았다
(`test_the_evidence_line_names_no_place_and_no_product`) — 음식점·카페·외식·마트·
장보기·배달이 전부 금지어다. 장을 보든, 나가서 먹든, 시키든, 선택적 끼니를 거르든
전부 이 문장을 만족한다.

> **프롬프트가 아니다.** 시스템 프롬프트는 양쪽 팔 모두 v25 다.
> 바뀌는 것은 **입력에서 같은 사실을 어디에 적느냐**뿐이다.

### 출발점

```
막힌 칸   46 · 47 · 42 · 44  / 96   (평균 44.8)
```

### 판정 — v10 과 같은 선

| | 기준 |
|---|---|
| **성공** | 막힌 칸이 **10 이하** |
| **부분** | 11 ~ 30 |
| **실패** | 31 초과 — 자리를 옮겨도 안 지킨다 |

**성공을 취소하는 조건**

| | |
|---|---|
| 끼니 회피 | 끼니 활동이 계획에서 거의 사라지면 충족이 아니라 회피다 |
| 계약 파손 | 계획 유효가 384/384 아래로 떨어지면 문장이 형식을 깨뜨린 것이다 |

### 기록만 하는 것

장보기 · 매장 취식 · 포장 · 배달 · 집밥 감소 중 무엇으로 풀었는지 센다.
**점수로 쓰지 않는다.** 어느 해법이 낫다고 정하는 순간 유도가 된다.

### 왜 이것이 v5 와 다른가

v5 도 "JSON 안의 사실을 산문으로 올린다"였고 실패했다. 다른 점은 둘이다.

1. **잣대가 다르다.** v5 의 주 지표는 도달 비율(칸당 0.1 수준, 위약 흔들림 0.094)이었다.
   여기는 막힌 칸 수이고 **46 대 0 규모**다
2. **작동하는 짝이 있다.** 세탁은 같은 형식으로 적혀 있고 **실제로 지켜진다.**
   v5 에는 비교할 짝이 없었다

그래도 실패할 수 있다. 그때는 **문장의 자리가 아니라 다른 것이 원인**이라는 뜻이고,
남은 후보는 `home_meal` 이 계획에서 채움 활동으로 쓰인다는 것이다.

## 결과 — 실패

계획 **384/384 유효**, 사후 보정 0.

```
막힌 칸 / 96        66001  66002  66003  66004   평균
대조 (v10 의 v25)     46     47     42     44    44.8
처치 (산문 한 줄)      47     42     45     44    44.5
```

**차이 −0.3 칸.** 판정선 "10 이하 성공 / 31 초과 실패" 로 **실패**다.

### 세 실험이 한 곳으로 모인다

| 라운드 | 무엇을 바꿨나 | 막힌 칸 |
|---|---|---:|
| v9 | 끼니 필요를 넣음 (기준선) | 45.5 |
| v10 | 시스템 프롬프트의 검사 범위를 명시 | 46.0 |
| v11 | 요구를 세탁과 같은 산문 한 줄로 | 44.5 |

**어구도 자리도 움직이지 않는다.**

### 남은 설명 — 모델이 고른 활동에는 자원 산술을 하지 않는다

세탁과 끼니의 남은 차이는 셋이다.

1. 세탁의 소비 활동 `provided_laundry` 는 **입력이 주입한 확정 활동**이고,
   끼니는 모델이 자유롭게 고르는 보통 활동이다
2. 세탁의 보충은 **온라인, 집에서** 된다. 끼니의 보충(장보기)은 나가야 한다
3. 세탁 필요의 충족 경로는 **하나**, 끼니는 넷이다

그런데 **2번은 변명이 못 된다.** `home_delivery` 는 집에서 되고 재고를 쓰지 않는다.
모델은 `home_meal` 을 `home_delivery` 로 바꾸기만 하면 됐고, 그렇게 하지 않았다
(96칸에 3건). `home_meal` 이 **공짜**이고 배달은 13,000원이기 때문으로 보인다.

**모델은 `home_meal` 을 무료 기본값으로 놓고 다시 보지 않는다.**

### 그래서 결론

**계획 단계 프롬프트로는 이 실패를 고칠 수 없다.** 어구(v10)와 자리(v11)를
모두 시험했고 둘 다 아무 일도 없었다. 남은 것은 모델이 자기가 고른 활동에
자원 산술을 하지 않는다는 것이고, 그것은 이 설정에서 **프롬프트로 표현되는 문제가 아니다.**

### 다음 — 게이트를 되먹임으로 쓴다

엔진에 이미 답이 있다. **게이트가 무엇이 부족한지 정확히 안다.**

```
{"event_id": "event:3", "time": "16:00", "resource": "meal_stock",
 "maximum_available": 0, "required": 1}
```

지금은 이 판정을 **거부에만** 쓴다. 이것을 모델에게 돌려주고 다시 계획하게 하는
길(`prepare_action_repair.py`)이 저장소에 있으나 **입력만 있고 모델 호출이 0회**다.
직전 인수인계가 "쓰려면 첫 실패·피드백·수정 출력을 모두 남기는 별도 프로토콜로
등록해야 한다"고 적어 둔 것이 이것이다.

**그것이 v12 다.** 프롬프트를 고치는 대신 **틀렸다는 사실을 모델에게 알려 주는**
실험이고, 사전등록도 다르게 해야 한다 — 수정본을 원본인 척 쓰면 안 되므로
첫 계획·게이트 판정·수정 계획을 전부 남긴다.
