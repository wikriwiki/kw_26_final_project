# v53 정책 파일럿의 소비 후처리 감사

이번 최종지출은 **같은 범용 v53 프롬프트를 사용하는 시뮬레이터 전체의 출력**이다. 프롬프트가 직접 제시한 계획금액이나 프롬프트 하나만의 효과가 아니다. Stage1 소비의향·Stage2 일정/금액/장소가 소득별 prior, 소비 앵커, 가격지수, 온라인 배분, 사용처·잔액·선택 결제 및 할인 정산을 거쳐 원장에 기록된다. 이 감사는 보존된 원장·실행 지문과 현재 소스/런처만 읽었다. 모델 호출·운영 코드·그래프·기존 numeric 파일은 변경하지 않았다.

| 설정 | 현재 코드 기본값 | 완료 실행에서 확인한 사실 |
| --- | --- | --- |
| `BAND` | 소득/성향 prior 중심 ±0.12; 코드 상수 | 최신 5정책 10팔 중 P012 ON을 제외한 9팔에서 처리 후 소비의향은 모두 중심 ±0.12 안에 있다. |
| `EXP_CASHBACK_BAND` | 0.30 | **실행 환경변수의 정확한 값은 미보존**이다. 별도로 P012 ON 372시민일 중 116건이 ±0.12 밖, 관측된 최대 차이는 0.30이다. P012 OFF는 0건·최대 0.12다. 기본값과 관측 범위를 동일한 증거라고 부르지 않는다. |
| `EXP_SPLIT_ANCHOR` | `0` | 모든 최신 10팔의 전 행에서 `cm_online_share_source=seoul_smallbiz`, 온라인 몫 0.7465다. 이는 실제 사용된 **split 비활성 분기**의 관측 증거다. 원 환경변수 문자열 자체를 회수한 것은 아니다. |
| `EXP_PLAN_DRIVES_TOTAL` | `0` | 정확한 환경변수 값은 미복원이다. 이 플래그가 꺼지거나 개인별 기준계획 파일/값이 없으면 모두 `max(anchor, planned)`로 되돌아간다. 원장 수식 일치만으로 둘을 구분할 수 없다. |
| `EXP_PAYMENT_CHOICE` | `1` | 최신 10팔 전 행에서 `cm_grant_choice_mode=true`: 실제 **건별 선택 결제 분기**가 켜졌다는 증거다. 적격 거래마다 지원금으로 자동 결제한다는 뜻이 아니다. |
| `COUPON_DAILY_DRAW_RATE` | 0.25 | 비 `EXP_` 이름이라 현재 `execution_fingerprint` 설정 목록에 **포함되지 않는다**. 정확한 실행값은 미보존이다. 다만 현재 선택 모드에서는 `_draw=1`로 덮어써 이 예전 배급 상한을 우회한다. |

위 최신 감사는 P010 ON/OFF 400시민일씩, P012 372씩, 거리두기 120씩, P016 200씩, P014 200씩이다. P013의 기존 보존 일별 아카이브도 별도로 읽었으며 ON/OFF 400시민일씩 모두 선택 결제 true, `seoul_smallbiz`, 온라인 몫 0.7465, prior ±0.12 밖 0건이다. 따라서 최종 JSON에는 **6정책 12팔**을 포함하고, P012 ON 116/372 관측을 말하는 최신 5정책 10팔 범위와 구분한다.

소비 총액은 현재 본문에서 `anchor = spend_today(p, daily_wd) × max(1, basket_index)`를 먼저 만들고, 기준계획 경로가 사용되지 않으면 `max(anchor, Stage2 planned_total)`을 쓴다. 이후 정해진 온라인 몫을 떼고 자기 잔액과 선택한 정책 결제·할인으로 감당할 수 있는 오프라인 거래를 정산한다. P010·거리두기·P016·P014 및 P013의 모든 행에서 `cm_personal_total + cm_online_total == max(cm_anchor_total, cm_planned_total)`이 관측됐다. P012는 ON 344/372, OFF 352/372만 이 등식에 맞는다. `cm_online_total`은 계획 온라인 금액이 아니라 잔액으로 제한된 실제 온라인 지출이므로 **불일치를 곧바로 계획 총액 플래그 활성으로 해석하지 않는다**.

split 비활성 경로에서는 Stage1의 `online_share`가 있어도 최종 비율을 정하는 데 쓰지 않는다. `1 - EXP_ELIGIBLE_SHARE` 기본값 0.7465가 실제 모든 팔에 기록됐다. 이 값의 코드 설명은 소상공인 소비 수준과 앵커 과대를 함께 교정하는 외부 비중이며, 시민이 독립적으로 배송 주문 몫을 바꾸었다는 증거가 아니다. 따라서 이번 온라인 금액 변화는 총액 변화와 고정 배분·잔액 후처리를 함께 반영한다. 온라인 결과를 프롬프트의 온라인/오프라인 선택 정확도로 읽으면 안 된다.

캐시백에는 또 다른 구조 차이가 있다. `run_simulation.py`는 활성 `ctx.policy`에 `type=cashback`이 하나라도 있으면 `cashback_active`를 전달하고, 소비 모듈은 그때만 별도 band를 고른다. **같은 범용 프롬프트여도 P012 ON과 OFF의 숫자 변환 허용폭이 다르다.** 실제 116건의 관측은 이 후처리 경로가 결과에 들어갔다는 근거이며, 정책 문구를 읽은 LLM의 선택 변화만으로 효과가 만들어졌다고 단정할 수 없게 한다. 해당 활성화 식은 신청 여부·연령을 검사하지 않는다. 다른 초기화/지급 경로의 자격을 모두 감사한 것은 아니므로 전국 신청자/수급자 모집단을 재현한다고 확대해석하지 않는다.

현재 코드 주석에는 과거 설계가 남아 있다. 파일 머리의 `spend_today = planned_total × day_multiplier`는 지금 본문의 앵커/max 식을 정확히 설명하지 않는다. 자동 지갑 우선배정이라는 설명도 실제 선택 모드에서 요청/선택이 없는 결제를 강제로 만들지 않는 본문과 구분해야 한다. 온라인 몫을 Stage1 판단 그대로 따른다는 주석도 기본 `seoul_smallbiz` 분기에 적용되지 않는다. 캐시백 경로 주석의 예전 grant 추가총액 설명과 달리 현재 본문은 `additional_from_grant=0`, `mechanical_policy_uplift=0`이며 모든 감사 행에서 해당 값이 0이다. **주석이나 옛 실험 설명보다 실행 본문·분기 메타데이터를 우선했다.**

보존 run_manifest는 개별 EXP 값을 저장하지 않았고 최신 frozen_inputs에는 consumption.py 개별 SHA가 없다. 다만 `source_fingerprint`는 `scripts/sim` 모든 Python 소스를, `execution_fingerprint`는 모든 `EXP_*`와 제한된 추가 설정을 포함한다. 양팔 동일 지문은 서로 같은 코드/설정 묶음을 썼다는 증거지만 **digest만으로 원 값을 복원할 수 없다**. 현재 런처의 whitelist를 검사한 결과 주요 네 플래그는 명시 배정되지 않았고 baseline seed 1·base ratio 0.268·balance days 39만 명시돼 있었다. 현재 런처와 코드 기본값만 보고 완료 프로세스의 상속 환경에 override가 없었다고 확정하지 않았다. `.env`나 DB/SSH 자격정보는 읽지 않았다.

현재 서버 consumption.py SHA는 `f99707c5662d6410e637460df54ac4194e4846d8d7ca049099a9e2caacc41c82`이며 로컬 CRLF를 LF로 정규화하면 정확히 같다. 현재 서버 전체 source 지문 `ddd8db11…`는 수정 후 P016/P014 원시 metrics와 같다. 이전 팔은 각자의 보존 전체 source 지문과 환경 지문을 별도 기록했다. 오래된 `source_commit`만을 실제 실행 소스 증거로 쓰지 않았다.

판정 범위는 다음과 같다. **동일 엔진·동일 입력·동일 기술 관문을 고정한 후보 프롬프트끼리의 비교는 가능**하다. 그러나 이번 v53의 정책 ON/OFF 최종지출 차이를 범용 프롬프트 단독 효과로 귀속하거나, 서로 다른 실측 추정량과의 일치로 최적 프롬프트라고 판정할 근거는 없다. 다음 정식 설계에서는 소비 후처리의 개인별 기준값·선택 분기·정책별 band·시드와 환경변수 실제 값을 함께 동결하고, 출력 계획과 정산 원장 차이를 별도로 평가해야 한다. 이번 결과를 보고 코드 폭이나 금액을 조율하지 않았다.

원시 감사: `output/multi_policy_v53_20260928/consumption_architecture_audit_20260928.json`; whitelist 런처 스냅샷: 같은 폴더 `consumption_launcher_snapshot_20260928.json`. 각 정책/팔의 원시 metrics 또는 P013 아카이브 member SHA, run_manifest/frozen_inputs SHA, 분기 카운트가 JSON에 있다.
