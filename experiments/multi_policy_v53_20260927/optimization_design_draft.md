# 범용 프롬프트 최적화 평가 설계 초안 — 2026-09-28

이 문서는 **아직 실험 사전등록 완료본이 아니다.** 후보 프롬프트 본문·입력·지표·관문을 모델 호출 전에 고정하고 Git 커밋 및 SHA256을 남겨야 그때부터 사전등록이다. 한 개의 범용 시스템 프롬프트에 정책별 규칙과 당시 배경을 별도 입력으로 주입한다. [실측 등록부](empirical_registry.json)의 결과값·기대 부호·허용 오차·정책별 예시는 모델 입력에 넣지 않는다.

## 무엇을 최적화할 수 있는가

기존 채점표 38개 중 원문에서 수치 실측을 확인한 지표는 15개다. 나머지 23개는 실측 대 시뮬레이션 수치 비교나 후보 순위에 쓰지 않는다. 15개도 현재 짧은 시민 ON/OFF 원장의 분모·기간·모집단·추정식과 대부분 다르다. **현재 3일 P013과 진행 중인 단기 정책 실험에서 외부 효과 크기 오차를 직접 계산해 프롬프트를 고를 수 있는 지표는 0개**다. 두 수치를 같은 표에 표시해도 원문의 전년동기 변화·삼중차분 계수·상품별 판매액을 며칠간의 시민 ON/OFF 지출률에서 빼지 않는다.

## 후보 선택 규칙

첫 비교는 `v53` 대 **단 하나의 범용 후보**로 제한한다. v53은 이미 “평소 용건→실제 정책 조건→시민 잔액·시간→Stage2 결제” 절차를 말한다. 그것을 반복하면 새로운 원인을 식별하기 어렵다. 대신 [v54 예시 계약 후보](candidate_v54_example_manifest.json)는 **Stage1 공통 시스템 본문의 출력 예시와 바로 뒤 설명 한 연속 구간만** 고친다. 기존 예시는 시간 19:00 뒤 17:30이 오고, 11개 일정 뒤 `...`가 있어 JSON이 아니며, 마지막 집 이벤트가 없다. 새 예시는 기존 장소 이벤트 6개에 직장 체류 3개와 귀가 1개를 더한, 시간순 10개 완결 JSON이다. 평일 직장인의 09~18시 누적 근무 4시간 이상 조건도 만족한다. 빼낸 미용·쇼핑 이벤트를 ‘위 예시’에 있다고 말하던 설명도 정합시켰다. 정책 사실·행동 목표·실측 숫자·Stage2는 건드리지 않는다. 정책별 조건·기대 방향을 하드코딩하지 않는다. [후보 화면 초안](candidate_v54_prereg_draft.json)은 같은 시민/정책 입력과 디코딩 조건을 고정한 첫 원시응답 형식 비교만 사전 지정한다. 과거 v10에서 예시를 아예 제거하자 악화된 적이 있으므로 예시를 유지하고 모순만 제거한다.

이 후보는 **형식 계약 개선 가설**이지 정책 효과 크기를 맞추는 행동 프롬프트라는 주장이 아니다. 후보 본문을 실행하기 전 별도 SHA256·Git 커밋으로 고정하고, 운영 중인 v53 모듈 파일은 변경하지 않는다. Stage2 공통 본문, 정책 JSON, 환경, 시민·소득 상태, 모델 서버, 출력 스키마, 온도, 시드, 날짜와 채점 코드는 두 후보에서 고정한다. 한 번에 Stage1과 Stage2를 모두 고치면 변화 원인을 구분할 수 없다.

후보가 통과해야 하는 순서는 다음과 같다.

1. **실행·형식 관문:** 동결 96개 맥락의 첫 원시응답에서 (A) 기존 v3 JSON/시간/장소 계약 **92/96 이상**, (B) 여기에 이벤트 상한·정확한 최상위 필드·존재하지 않는 직장 anchor 금지를 더한 구조 계약도 **92/96 이상**을 동시에 요구한다. 두 계약 모두 새 v53 쌍체 응답보다 실패가 많지 않아야 하며, 요청 실패 0·무정책 재정 팔의 허위 정책 귀속 선별 플래그 0이어야 한다. 92/96은 95.8%다. 기존 일반 출력·온도 0 화면은 v3에서 96/96이었지만 83/96이 10개 상한을 넘었다. 상한을 빠뜨린 성공률로 후보를 통과시키지 않는다. 평일 직장 체류 4시간은 별도 진단으로 보고한다. 후처리 보정은 최초 통과로 세지 않는다. 생산 시뮬레이션의 최종 `status=ok`는 재시도 후 성공이며 첫 원시응답 형식률이 아니다. `metrics/attempts`의 외부 재시작 이전 실패까지 보존하고, 첫 시도 *내부 검증* 통과율을 별도로 표시하되 원시 엄격 형식률과 동일시하지 않는다. Stage2 실제 선택, 정산, 지갑·월말 캐시백, 금지 업종, 비대상·기간 밖 시민을 별도로 검사한다. 장소 자동 대체나 원장 불일치가 있으면 외부 효과 크기를 평가하지 않는다. 과거 v53 Stage1은 생산 온도에서 350/384(91.1%)로 A 관문에 실패했으므로 새 후보도 예외 처리하지 않는다.
2. **쌍체 선행기간 관문:** 같은 시민·날짜·소득 지도·시드에서 정책 발효 전 ON/OFF 거래와 노출이 평형인지 확인한다. 아직 신규 결과를 보지 않은 P010/P016/P014의 선행 2일은 총기록지출의 절대 차이가 OFF 대비 **10% 이내**, 해당 업종 POI 대리 매출의 절대 차이가 OFF 대비 **20% 이내**여야 통과한다고 미리 정한다. OFF 분모가 0이면 임의 보간하지 않고 통과 불가로 둔다. P010의 업종 대리는 정확한 쿠폰 사용가능 매장 명부가 아니라 오프라인 총액이므로 한계가 남는다. P012/거리두기에는 이 2일 선행기간이 없어 해당 관문을 통과했다고 표시하지 않는다. 기존 P013은 이 문턱을 소급 적용하지 않는다. 차이가 남으면 이후 ON/OFF 숫자는 기술 진단으로만 보고 정책 인과효과라고 부르지 않는다. 정책이 시행되지 않은 팔에 지급·결제액이 새면 즉시 실패다.
3. **개발 정책의 일반화 진단:** P010·P012·P013은 이미 확인한 개발 자료다. 사전 고정한 지표의 방향·시민 이질성·지출 재원·업종 재배분을 각 정책별로 보고, 효과가 한 정책에서만 커지거나 다른 정책에서 무너지면 탈락한다. 같은 정책에서 지표 수가 많다고 가중치를 더 주지 않는다. 그러나 현재 대리 지표로 외부 수치와의 거리 함수를 만들거나 “실측 적중” 순위를 매기지 않는다.
4. **잠금 교차정책 확인:** 후보 본문과 채점 규칙을 고정한 뒤 거리두기·P016에서 단 한 번 같은 방식으로 실행한다. 두 정책의 원문 결과와 기존 v5 탐색은 이미 일부 알려져 있으므로 이는 **독립적인 맹검 홀드아웃이 아닌** 교차정책 스트레스 검사라고 표시한다. 결과를 보고 후보를 다시 고치면 이 확인셋도 개발셋으로 이동한다.

향후 진짜 효과 크기 검증에서는 지표마다 **동일 모집단·기간·단위·분모·대조군·추정식**을 사전 감사해 통과시킨 뒤에만 오차를 계산한다. 부호가 맞는지와 대략 크기가 맞는지를 분리 보고한다. 큰 양의 비율 지표는 사전 지정한 예컨대 0.5~2배 범위 같은 **지표별 해석 가능한 구간**으로 크기 등급을 판단하고, 0 근처·%p·로그계수는 원문 표준오차와 의미 있는 차이를 기준으로 따로 정한다. 이 범위를 결과를 본 후 조정하지 않는다. 여러 정책의 수치를 단위가 다른 채 더하거나 원시 절대차 평균을 최소화하지 않는다.

## 이번 12시간의 현실적인 완료선

우선 현재 v53 각 정책 ON/OFF 런을 끝까지 실행하고 원장·모델 스냅샷·정책 입력을 서버 밖에 SHA256으로 보존한다. 완결된 지표만 실측과 시뮬 수치를 나란히 실은 HTML을 만든다. 10:45 KST 보고 전 신규 후보까지 비교하려면 **현재 v53 백업 완료 후** 위 단락을 확정·해시하고 기존 동결 12명×여러 기전의 Stage1 첫 응답을 v53과 같은 조건으로 쌍체 실행하는 기술 화면이 첫 단계다. GPU 단일 서버와 현재 런을 방해하지 않는다. 이 화면을 끝내고 남는 시간에만 개발 정책 중 한 개의 짧은 Stage2·ON/OFF 쌍체 파일럿을 진행한다. 새 모델 호출은 늦어도 08:30 KST에 중지하고 점수·SHA·HTML 감사 시간을 남긴다.

이 제한 아래 가능한 결론은 “범용 후보가 v53보다 형식/회계/미시 행동 관문을 개선했는가”와 정책별 **대리 수치의 방향·대략 범위가 어디에 놓였는가**다. 직접 정합 지표가 없거나 잠금 정책의 완결 런이 없으면 “범용 최적 프롬프트가 실측 효과의 방향과 크기를 검증했다”는 결론은 내리지 않는다. 후보가 실패하거나 시간이 모자라면 v53 결과와 실패 원인을 그대로 보고하고 임의로 유리한 팔만 골라 최적화 성공으로 선언하지 않는다.
