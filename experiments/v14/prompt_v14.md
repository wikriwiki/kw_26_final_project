# 실험 v14 — 되먹임 루프를 반복하면 수렴하는가

**날짜 2026-09-21** · **상태** 완료 — **수렴한다. 다만 느리고 0에 닿지 않았다**
**프롬프트 v25 동결** · 판정선은 v13 에서 이어받았다(10 이하 성공)

---

## 왜 돌렸나

v13 에서 게이트 판정을 한 번 돌려줬더니 **방향은 맞고 크기가 모자랐다** —
`home_meal −9 · home_delivery +9 · groceries +3` 인데 막힌 칸은 46 → 44 였다.
재고 0에 끼니가 둘인데 **한 끼만 고쳤다.**

그러면 **한 번 더 돌리면 나머지도 고치는가**가 바로 다음 물음이다.

> **사전등록 상태를 정확히 적는다.** v14 는 v13 의 결과를 보고 시작했다.
> 판정선은 v13 에서 정한 것(10 이하 성공)을 그대로 쓰고 **바꾸지 않았다.**
> 새 지표를 만들지도 않았다 — 같은 게이트, 같은 셈이다.

## 결과 — 줄어든다

```
바퀴      대상    수정 뒤 막힘     감소
0 (v12)   96        46           —
1 (v13)   46        44          −2
2         44        33         −11
3         33        21         −12
4         21        17          −4
```

**46 → 17.** 96칸 기준으로 **79칸이 물리적으로 가능해졌다**(82%).

### 판정

사전등록선은 **10 이하**였고 **17** 이다. **미달 — 성공으로 세지 않는다.**

다만 v13 의 44 와는 성격이 다르다. v13 은 "거의 안 줄었다"였고
여기는 **네 바퀴에 걸쳐 꾸준히 줄었다.**

### 모양이 말해 주는 것

```
−2 · −11 · −12 · −4
```

첫 바퀴가 유난히 작은 것은 **수정 표시가 견적 로직을 깨뜨린 버그**를 고치기 전
데이터가 섞여 있어서가 아니다 — 고친 뒤 돌린 것이다. 2·3바퀴가 큰 것은
**고칠 것이 많을 때 한 번에 하나 이상 고친다**는 뜻이고, 4바퀴가 작아진 것은
**남은 17칸이 어려운 칸**이라는 뜻이다.

**감소가 멈춘 것이 아니라 느려졌다.** 더 돌리면 더 줄 수는 있으나
바퀴당 비용이 남은 칸 수에 비례하므로 **끝까지 가는 비용은 알 수 없다.**

## 그래서 지금 말할 수 있는 것

| | |
|---|---|
| **프롬프트로는 못 고친다** | 어구·자리·순서 셋 다 무효 (v10·v11·v12) |
| **되먹임은 고친다** | 46 → 17. 다만 한 번이 아니라 네 번 |
| **완전하지 않다** | 17칸이 남았고, 그 행렬은 **불완전**이다 |

**불완전한 행렬을 온전한 비교로 읽지 않는다** — v1 에서 정한 규칙이고 여기서도 지킨다.
17칸을 뺀 79칸으로 정책 효과를 비교하면 **그것은 선택된 79칸의 성질**이다.

## 남은 일 — 순서대로

1. **루프를 파이프라인에 넣는다.** 지금은 손으로 네 번 돌렸다.
   `validate_action_planner` 다음에 게이트·수정이 자동으로 붙어야 한다
2. **남은 17칸이 왜 안 고쳐지는지 본다.** 어려운 칸의 공통점이 있으면
   그것이 다음 표적이다
3. **그 뒤에야 프롬프트를 다시 겨룬다.** 계획이 물리적으로 가능해져야
   정책 지표를 비교할 자격이 생긴다

## 이 라운드가 답하지 않는 것

- **최적 프롬프트** — 프롬프트를 건드리지 않았다
- 고쳐진 계획이 **옳은** 계획이라는 것 — 아니다. **가능해졌을 뿐이다**
- 몇 바퀴면 0이 되는가 — 모른다. 4바퀴에 17이고 감소가 느려지고 있다
