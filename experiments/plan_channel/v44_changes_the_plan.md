# v44 를 안 읽고 28일 런을 걸었다 — 전제가 이미 기각돼 있었다

**2026-09-24 20:15** · `experiments/v44/result_v44.md` 를 뒤늦게 읽음

---

## v44 가 이미 답한 것

```
v44 문턱 탐침 (2026-09-22)
  모델이 문턱까지의 거리에 **방향 없이** 반응한다 — 12명 중 11명이 비단조
  "누적을 더 쌓아도, 잃는다고 더 분명히 말해 줘도,
   문턱까지의 거리가 행동을 정하지 않는다"

그 결과로 두 라운드가 죽었다
  v30  관측 창을 **31일로 늘려** 누적을 쌓으면 캐시백 효과가 커지는가
       -> **18/31 일차에서 세웠다. 전제가 죽어서**
  v43  잘린 손실 프레임을 돌려주면 커지는가  -> 돌리지 않았다
```

그리고 v44 는 다음 표적을 이렇게 적어 두었다.

> P012 의 크기는 프롬프트로 못 맞춘다. 창도 절단도 원인이 아니고,
> **엔진이 문턱을 예산에 반영해야 한다.**

## 내가 오늘 한 것

```
diagnosis_06  "9일 창에서 91%가 문턱에 못 닿는다 -> 창을 28일로"
그리고 28일 런을 **회계 고침을 끈 채로** 걸었다
```

**그것이 v30 의 재실행이다.** v44 가 이미 "창으로는 안 된다" 를 보였는데,
나는 그 문서를 안 읽고 같은 실험을 다시 세웠다. 오늘만 세 번째다 —
정책 파일 notes, 채점표 expect, 그리고 이번엔 앞선 라운드 결과.

## 다만 오늘 한 일이 전부 헛것은 아니다

v44 가 가리킨 **"엔진이 문턱을 예산에 반영해야 한다"** — 그것이 바로
`EXP_PLAN_DRIVES_TOTAL` 이다. 계획의 정책 반응이 `max(앵커,계획)` 에서 버려지는
것을 개인 기준선으로 통과시키는 회계 고침이고, 오늘 만들어 세 겹으로 확인했다
(재계산+CI · LLM 없는 관문 · P013 표본 밖).

**v44 가 가리킨 방향과 오늘 만든 것이 같은 곳이다.** 다만 나는 그것을 모른 채
왔고, 그래서 **순서를 틀렸다** — 죽은 전제(창 단독)를 먼저 걸었다.

## 그래서 계획을 바꾼다

```
지금 도는 것   28일 창 · v5 · 회계 고침 **꺼짐**   <- v30 의 재실행. 값이 적다
바꿀 것        28일 창 · v5 · 회계 고침 **켜짐**   <- v44 가 가리킨 엔진 수정
```

**창을 버리지는 않는다.** 창은 크기를 못 키우지만(v44), `P012-3·4·6`(문턱 도달·
캐시백·한도)이 값을 내려면 누적이 쌓일 시간이 필요하다. 창은 **그 지표들이
존재하게 하는 조건**이지 크기를 키우는 장치가 아니다 — 그 구분을 v44 가 가르쳐 줬다.

## 실행

```
1  지금 런을 3일차까지 두고 멈춘다 (워밍업 3일이면 개인 기준선을 만들 수 있다)
2  그 3일로 /data/plan_baseline_28d.json 을 만든다
3  28일 전체를 **회계 고침 켜고** 다시 건다
```

28일을 두 번 도는 것(30시간)보다 **3일 + 28일(16.5시간)** 이 낫다.
죽은 전제에 15시간을 더 쓰지 않는다.
