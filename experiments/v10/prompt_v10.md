# 실험 v10 — 자기가 고른 활동에도 자원 검사를 걸게 한다

**날짜 2026-09-21** · **상태** 완료 — **실패. 어구는 지렛대가 아니었다**
**양쪽 모두 끼니 필요 모형을 쓴다** (v9 에서 만든 `action_source_meal.json`)

---

## v9 이 만든 상황

끼니 필요를 넣자 **자원 게이트가 96칸 중 46칸을 막았다.**

```
        seed66xxx 기준 전 단계 (v9, 65001~4)
laundry (필요 하나)      0 · 0 · 0 · 1  막힘
meal    (필요 둘)       46 · 46 · 45 · 45  막힘
```

막힌 칸은 **전부 `meal_stock` 0 인 시민**이고, 이유는 하나다.

```
16:00 home_meal   ← 재고 0, 필요 1
19:00 home_meal   ← 재고 −1, 필요 1
장보기 · 외식 · 배달  계획에 없음
```

전체로 봐도 **재고 0인 시민이 재고 2인 시민보다 집밥을 더 계획한다**(102 대 75).

## 그런데 프롬프트는 이미 그렇게 하라고 말한다

```
v25:  daily_conditions가 있으면 활동에 필요한 자원을 실제 사용 전 확보할 수 있는지 확인한다.
```

**세제는 지킨다** — 재고 0이면 온라인으로 주문한다.
**끼니는 안 지킨다.** 차이는 세탁이 `provided_laundry`(입력이 주입한 확정 활동)이고
끼니는 **모델이 자유롭게 고르는 보통 활동**이라는 점뿐이다.

가설: **모델이 자원 검사를 '주어진 활동'에만 적용한다.**

## 무엇을 바꾸나 — 어구 하나

```
v25   daily_conditions가 있으면 활동에 필요한 자원을 ...
v32   daily_conditions가 있으면 배치하는 모든 활동에 대해 필요한 자원을 ...
```

**해법을 지정하지 않는다.** 채우든(장보기), 나가서 먹든, 시키든, 선택적 끼니를
거르든 전부 이 지시를 만족한다. 하나를 지목하면 유도이므로 검사로 막았다
(`test_it_does_not_say_how_to_solve_it`).

> **이것이 정책 결과 유도가 아닌 이유** — 정책 이름도, 방향도, 업종도 없다.
> **이미 있는 지시를 지키게 하는 것**이고, 지키는 방법은 넷 다 열려 있다.

## 사전등록

| | 내용 |
|---|---|
| 설계 | 같은 12명 × 4기전 × on/off = 96칸, seed 4개(66001~66004), 두 팔 = 계획 768칸 |
| 원본 | **양쪽 모두 끼니 필요 모형** (`action_source_meal.json`, sha256 `20940296…`) |
| 다른 것 | 프롬프트 어구 하나뿐 |
| 실행 | **계획 + 게이트까지만 먼저 돌린다.** 게이트는 모델을 부르지 않으므로 공짜다 |

### 출발점 (v9, v25 + 끼니 모형)

```
막힌 칸   46 · 46 · 45 · 45  / 96
```

### 판정 — 주 지표는 막힌 칸 수

| | 기준 |
|---|---|
| **성공** | 막힌 칸이 **10 이하** (46 에서) |
| **부분** | 11 ~ 30 |
| **실패** | 31 초과 — 어구를 바꿔도 자기가 고른 활동은 검사하지 않는다 |

**성공을 취소하는 조건**

| | |
|---|---|
| 끼니 회피 | 계획에서 끼니 활동이 거의 사라지면(집밥 포함) 필요를 **충족한 것이 아니라 피한 것**이다 |
| 계약 파손 | 계획 유효 건수가 384/384 아래로 떨어지면 어구가 형식을 깨뜨린 것이다 |

### 기록만 하는 것 — 어떻게 해결했나

장보기 · 매장 취식 · 포장 · 배달 · 집밥 감소 중 무엇으로 풀었는지 센다.
**점수로 쓰지 않는다.** 어느 해법이 낫다고 정하는 순간 유도가 된다.
다만 이것이 v11 에서 무엇을 겨룰지를 정해 줄 것이다.

### 게이트를 통과하면

그때 결제를 돌리고 17개 지표를 낸다. **통과하지 못하면 결제를 돌리지 않는다** —
불완전한 행렬을 온전한 비교로 읽지 않는 것이 v1 에서 정한 규칙이다.

### 이 실험이 답하지 않는 것

- **최적 프롬프트** — 계획이 물리적으로 가능해지는 것이 먼저다
- 가능한 계획이 옳은 계획이라는 것 — 아니다. 잴 수 있게 될 뿐이다
- 끼니 외의 업종 — 건강·미용·여가는 여전히 필요가 없다

## 결과 — 실패

두 후보 모두 계획 **384/384 유효**, 사후 보정 0.

```
막힌 칸 / 96        66001  66002  66003  66004   평균
v25 (현직)            46     47     42     44    44.8
v32 (범위 명시)        46     45     46     47    46.0
```

**차이 +1.2 칸.** 판정선은 "10 이하면 성공, 31 초과면 실패"였고 **실패**다.

"배치하는 **모든** 활동에 대해"라고 못 박아도 모델은 자기가 고른 `home_meal` 에
자원 검사를 걸지 않는다. **어구가 지렛대가 아니다.**

### 그럼 세제는 왜 되나 — 찾았다

입력을 다시 봤더니 두 요구가 **서로 다른 자리에** 적혀 있다.

```
세탁   "실험 가정: provided_laundry는 집에서 세탁 1회를 하는 활동이며,
        실제 시작 전에 세제 1회분이 있어야 한다."      ← JSON 앞, 산문 한 줄

끼니   meal_stock · 식재료 · 한 끼분 은 전부 JSON 안에만 (resources·assumptions)
```

세탁의 요구는 **조건 블록 맨 앞에 산문 한 줄로** 서 있고,
끼니의 요구는 **JSON 필드 안에 묻혀 있다.**

`add_meal_need.py` 가 `activity_consumption` 과 `assumptions` 만 채우고
**증거 줄을 만들지 않았다.** 내가 세탁과 같은 구조라고 했는데, 한 조각이 빠져 있었다.

### 그래서 v11

프롬프트는 다시 v25 로 두고, **끼니 요구를 세탁과 같은 형식의 산문 한 줄로** 적는다.
대조군은 **이 라운드의 v25 팔 그대로**다 — 같은 프롬프트, 같은 seed, 원본만 다르다.
그래서 처치 팔만 돌리면 된다.
