# 실험 v2 — 게이트를 낀 채로 처음부터 끝까지 한 번 돌린다

**날짜** 2026-09-20 · **프롬프트** 계획 `v25` · 결제 `asset_transaction_v7` (**변경 없음**)
**상태** 사전등록 완료, 실행 대기

---

## 이번에 바뀐 점

**프롬프트는 또 바꾸지 않았다.** v1에서 붙인 자원 게이트를 **실제 실행 경로에 처음
태운다.** 지금까지 게이트는 단위검사에서만 동작했다.

그리고 **새 seed(58001)** 로 계획을 새로 뽑는다. 이전 런의 행을 다시 채점하는 것이
아니라 **새로 뽑은 96칸**이다. 게이트가 이미 본 실패 하나를 막는지 확인하는 것으로는
부족하다 — 새 계획에서도 파이프라인이 온전한 행렬을 내는지가 물음이다.

## 눈여겨 볼 점

**① 이 실험은 프롬프트 성능을 겨루지 않는다.** 직전 인수인계가 남긴 물음은
"v25가 최적인가"가 아니라 **"측정 경로가 온전한 행렬을 낼 수 있는가"** 다.
그게 안 되면 어떤 정책 효과도 읽을 자격이 없다.

**② 왜 프롬프트를 아직 안 건드리나.** 정답(실측 효과)을 보고 프롬프트를 고치면
순환 검증이다. 사용자가 처음부터 못 박은 규칙이고, 검증 아키텍처 감사가 v5의
"부호 12/12"를 무너뜨린 이유 중 하나이기도 하다. **측정이 믿을 만해진 뒤에야**
프롬프트를 비교할 수 있다.

**③ 프롬프트 오염은 이미 해결돼 있다.** v5를 무너뜨린 결함 — p012 본문만 갈아끼워
캐시백 문턱·10%·사용처 예시가 공통 지시에 남았던 것 — 을 v25·v7에서 확인했다.
정책 이름·원하는 방향·실측 목표가 **하나도 없다.** 그래서 v2에서 고칠 것이 없다.

**④ 게이트가 0건을 막아도 성공이다.** 새 계획이 전부 물리적으로 가능하면 게이트는
아무것도 막지 않고, 그때 비로소 **자격 있는 완전 행렬**이 나온다. 반대로 한 칸이라도
막히면 그 사실을 적고 **남은 칸을 온전한 비교로 읽지 않는다.**

## 사전등록

| | 내용 |
|---|---|
| 설계 | 같은 12명 × 4기전 × on/off = **96칸**, 1일, 새 seed **58001** |
| 계획 | `v25`, thinking 512 / answer 2048, 온도 0.2, 30분 문법, 18시 이후 마지막 집 활동 |
| 결제 | `asset_transaction_v7`, v4 선택 문법, 결제 seed 53001 (이전 경로와 동일) |
| 게이트 | 계획→결제 사이에서 물리적 불가능을 판정. **기본 거부**, 제외 시 행렬을 불완전으로 표시 |
| 엔진 | on/off 양쪽에 같은 엔진. 프롬프트·계약·소스 전부 동결 |

### 판정 기준 — 돌리기 전에 정한다

| 항목 | 통과 조건 |
|---|---|
| 계획 완전성 | 96/96, 요청 실패 0, 사후 시각 보정 0 |
| 게이트 | 막힌 칸 수를 **그대로 보고**한다. 0이면 행렬 자격 성립 |
| 결제 완전성 | 게이트를 통과한 모든 칸이 응답을 남긴다. 실패는 보존한다 |
| 회계·물리 | 원문 회계 검사와 재고·배송 검사를 독립으로 통과 |
| 기전별 대조 | **완전 행렬일 때만** on/off 차이를 낸다. 아니면 `not_scored` |

**하면 안 되는 것** — 실패 행을 빼고 평균 내기, 0원으로 메우기, 막힌 계획의 시각
고치기, 성공한 칸만으로 "검증 성공" 만들기. 전부 직전 인수인계가 금지한 것이다.

### 이 실험이 답하지 않는 것

- 최적 프롬프트가 무엇인지 — **겨루지 않는다**
- 실제 정책 효과의 크기가 맞는지 — 12명·1일·1반복으로는 못 낸다
- 새 정책에 일반화되는지 — 새 홀드아웃이 아니다
