## 1. 원래 무엇이 문제였나

### 1-1. 증상

에이전트가 점심으로 **김밥천국**을 고르든 **오마카세**를 고르든, 그날 쓰는 돈이 똑같았다.

### 1-2. 원인은 코드의 두 곳

**(원인 A) 후보 목록에 가격 정보가 아예 없었다.**

Stage2(장소 선택) LLM이 보는 후보 목록은 이렇게 생겼었다:

```
C_000001 | 김밥천국       | 0.20km | 신규
C_000002 | 오마카세 스시젠 | 0.50km | avg_sat=0.80 (3회)
```

이름·거리·과거 만족도뿐. **가격 신호가 0**이라 LLM이 예산을 고려해 고르는 것 자체가 불가능했다.

**(원인 B) 금액이 사후 재정규화로 뭉개졌다.** — 더 근본적인 원인

LLM이 "오마카세 8만원"이라고 적어도, 그 숫자는 **상대 비율로만** 쓰였다.
실제 하루 총지출은 `consumption.py`에서 이렇게 **다시** 계산됐다:

```
하루 총지출 = 소비성향(p) × 가용자산        ← 어느 가게를 골랐는지와 무관!
각 거래 금액 = 총지출을 LLM 비율대로 나눔
```

즉 오마카세를 골라도 하루 총액은 그대로이고, 단지 그 고정 총액 안에서
"오마카세 몫"이 커질 뿐이었다. **가게 선택 → 지출 변화**라는 인과가 구조적으로 차단돼 있었다.

### 1-3. 왜 고쳐야 했나

- 현실에서는 비싼 식당에 가면 그날 지출이 늘고 잔액이 준다.
- 곧 도입할 **판매자 에이전트**의 핵심 행동이 "가격 조정"인데,
  소비자가 가격에 반응하지 않으면 판매자의 가격 인상/인하가 **아무 효과가 없는** 시뮬이 된다.

## 2. 새 알고리즘 — 돈이 결정되는 전체 흐름

바뀐 후의 하루를 따라가 보자.

```
새벽  ┌─────────────────────────────────────────────────────┐
      │ 에이전트 상태 로드: 잔액(balance), 평소 소비규모(daily_wd) │
      └─────────────────────────────────────────────────────┘
낮    ┌─ Stage2 (장소 선택) ────────────────────────────────┐
      │ 프롬프트에 새로 들어간 것:                            │
      │  ① 헤더: "현재 잔액: 152,000원"                      │
      │  ② 이벤트 제목: "동네 평균단가 ~12,000원"  ← 실측 앵커  │
      │  ③ 후보마다: ₩ / ₩₩ / ₩₩₩  가격대 아이콘             │
      │  ④ 규칙: "잔액 빠듯하거나 절약형이면 ₩ 위주로"          │
      │ → LLM이 예산·성향·가격대를 맞춰 가게 선택 + 금액 제안    │
      └────────────────────────────────────────────────────┘
      ┌─ 금액 확정 (consumption.py) ─────────────────────────┐
      │ 기본 총액 = 소비성향 p × 가용자산          (기존 그대로) │
      │ 장바구니 가격지수 = 오늘 고른 가게들의 가중평균 가격배율   │
      │ 최종 총액 = 기본 총액 × 가격지수  (0.8~1.25로 제한)     │
      │ 거래별 배분 가중치 = LLM 제안액 × 그 가게 가격배율        │
      └────────────────────────────────────────────────────┘
밤    ┌────────────────────────────────────────────────────┐
      │ 잔액 = 어제 잔액 − 오늘 지출 합   (기존 쿼리 그대로)      │
      │ → 내일 Stage2 헤더의 "현재 잔액"이 달라짐                │
      └────────────────────────────────────────────────────┘
```

**루프가 어떻게 닫히나**: 비싼 곳 선택 → 총액 ↑ → 잔액 ↓ → 다음날 프롬프트의 잔액이 줄어듦 → LLM이 ₩ 후보를 선호. (단, 이 마지막 화살표는 수식이 아니라 **LLM의 프롬프트 해석**으로 작동한다 — §6-3 참고.)

### 숫자 예시

절약형 직장인(평소 3만원/일), 점심 이벤트 하나라고 하자.

| 시나리오 | 고른 가게 | 가격배율 | 하루 총지출 |
|---|---|---|---|
| 저가 | 김밥천국 (₩, 0.75) | 0.80 (클램프 하한) | **25,371원** |
| 기본 | 백반집 (₩₩, 1.00) | 1.00 | 31,714원 |
| 고가 | 오마카세 (₩₩₩, 1.35) | 1.25 (클램프 상한) | **39,642원** |

(consumption.py 자체 테스트 ⑤의 실제 출력값. 이전에는 세 경우 모두 같은 금액이었다.)

## 3. 가격은 어디서 오나 — 데이터 이야기

### 3-1. 이상적으로 필요한 것과, 실제로 존재하는 것

이상: "김밥천국 김밥 4,500원" 같은 **가게별 실제 가격**.
현실: 그런 데이터는 부분적으로만 존재한다. 그래서 **실측 우선 3계층**으로 설계했다 —
좋은 데이터가 있으면 그걸 쓰고, 없으면 한 단계씩 물러난다.

### 3-2. 핵심 발견 — 버려진 줄 알았던 실측 단가의 복원

우리 레포의 `dong_consumption.json`(BDC 신용카드 데이터 가공본)에는 동네(행정동)마다
`카드이용금액계`와 `카드이용건수계`가 들어 있는데, 전처리 때 **비율로 정규화**되어
절대값(원)이 사라진 상태였다.

그런데 두 값을 **나누면** 정규화 분모가 약분되어 사라진다:

```
金정규화 = 금액 / (금액+건수),   件정규화 = 건수 / (금액+건수)

金정규화 ÷ 件정규화 = 금액 ÷ 건수 = 평균 결제단가(건단가)   ← 분모 소멸!
```

즉 **동네별 "카드 한 번 긁을 때 평균 얼마"라는 실측값**이 복원된다.
426개 동 전부에서 복원됐고, 상식과도 맞는다(강남 코드들이 상위권, 외곽 주거지가 하위권).

### 3-3. 3계층 구조 (좋은 데이터부터 차례로)

```
① [POI 개별]  카카오 메뉴가격                    ← 가게 단위 실측 (준비됨, 실행 대기)
      크롤해 둔 카카오 상세패널 원본(raw_json)에서 메뉴·가격 추출.
      가게 대표가 = 메뉴 중앙값 → 같은 업종 내 백분위로 ₩/₩₩/₩₩₩ 판정.
      * 추출 스크립트는 만들어 뒀고, 크롤 머신에서 실행해야 함 (§7)

② [동네 수준]  BDC 카드 건단가 (§3-2 복원값)      ← 동 단위 실측 (지금 작동 중)
      동네 건단가 → "동 가격계수"로 변환 (비싼 동네 최대 +16%, 싼 동네 −13%)
      가게 개별 차이는 결정론적 해시로 ₩/₩₩/₩₩₩ 배정 (분포 30/50/20)

③ [최후 fallback]  기존 방식                     ← 데이터 파일 없어도 동작
      발달지수 순위 동 계수 + 하드코딩 업종 단가표
```

**합성 규칙 한 가지 주의점(이중계상 방지)**: ①의 메뉴가는 이미 "그 동네 물가"가 반영된
절대 가격이므로, ①을 쓸 때는 ②의 동 계수를 **곱하지 않는다**. 곱하면 강남 프리미엄이
두 번 계산된다.

### 3-4. "동네 평균단가" 앵커

LLM이 금액을 지어내지 않도록, 이벤트 제목에 실측 스케일을 박아준다:

```
### 이벤트 0 | 12:00 | 역삼1동 | 식사/한식 | 점심 | 동네 평균단가 ~12,000원
```

= (업종 기준단가) × (그 동네 가격계수). 업종 기준단가는 현재 하드코딩 표(식사 12,000원 등)를
쓰지만, 서울시 공공 CSV(§7)를 넣으면 **실측 업종 단가로 자동 교체**된다.

### 3-5. 왜 순환성 문제가 풀리나 (검증 관점에서 중요)

이전 버전(첫 커밋)의 동 가격계수는 `b069_sales`(상권발달지수 **매출** 지수)를 썼다.
그런데 이 변수는 이미 ① 광역이동(Huff)의 매력도이자 ② **공간 검증의 정답 데이터**다.
같은 변수가 세 곳에 쓰이면 "검증이 잘 나와도 자기 자신을 맞춘 것"이라는 비판을 받는다.

새 버전은 **건단가**(단가 강도)를 쓴다. 매출 규모와 상관 0.61 — 관련은 있지만 다른 축.
실제로 역삼1동의 가격계수가 1.107(매출 기반) → **1.011**(단가 기반)로 바뀌었다.
"매출 1위 동네 ≠ 단가 1위 동네"라는 실측 사실이 반영된 것.

## 5. 안전장치 — 기존 검증이 깨지지 않게

이 프로젝트는 cosine/JSD/Gini/MPC로 외부 검증을 해 왔다. 그걸 지키는 장치들:

1. **평균 1.0 캘리브레이션**: 가격배율의 도시 전체 기대값 ≈ 1.0
   (밴드 30/50/20 × 0.75/1.00/1.35 = 0.995, 동 계수 평균 = 정확히 1.0).
   → 개인의 하루는 오르내리지만 **집계 총량은 보존** → 총량 기반 검증 유지.
2. **클램프 (폭주 방지)**: 하루 가격지수 [0.8, 1.25], 가게 배율 [0.6, 1.6],
   지출 상한 = 가용자산의 98%.
3. **완전 하위호환**: 가격 정보가 없으면(구 데이터, 파일 부재) 배율이 전부 1.0이 되어
   **기존 코드와 동일하게** 동작. 자체 테스트에 assert로 고정해 둠.
4. **편의점·마트는 거의 균일가** (0.95~1.05): 현실 반영. 가격 분산은 식당·카페 등
   경험재에만 크게 준다.
5. **노이즈 방어**: 동 건단가의 극단값(소표본 동네)은 로그-z ±2σ에서 절단.

## 6. 정직한 한계 — 검토 시 같이 봐주면 좋은 것

### 6-1. 아직 합성인 부분

동네 **안에서** 어느 가게가 ₩이고 ₩₩₩인지는 (메뉴가 데이터가 붙기 전까지) 해시 배정이다.
분포(30/50/20)는 통제되지만 "이 김밥집이 진짜 저가인지"는 모른다.
→ Layer ①(카카오 메뉴가)이 붙으면 음식·카페부터 실측으로 바뀐다.

### 6-2. 업종 기준단가는 아직 하드코딩

"식사 12,000원, 카페 6,000원" 표는 경험 상수다. 서울시 공공 CSV(§7-1)를 넣으면
실측(업종×동 매출÷건수)으로 자동 대체되도록 파서까지 만들어 뒀다.

### 6-3. 잔액→선택 결합은 LLM 해석에 의존

"잔액이 줄면 ₩을 고른다"는 수식이 아니라 프롬프트 규칙이다. LLM이 무시하면 약해진다.
또 **잔액은 수입 유입 없이 감소만** 하는 구조(초기 150만원, 지원금 외 수입 없음)라,
장기 런에서는 날이 갈수록 저가 쏠림이 생길 수 있다.
→ **다음 GPU 런에서 확인할 것**: 날짜별 평균 지출에 하락 추세가 있는지,
  기존 6지표(V0 회귀)가 유지되는지, 소비 Gini가 실측 0.424를 넘지 않는지.

### 6-4. 사소한 것들

- 약속(pinned) POI는 후보풀을 안 거쳐 가격배율 1.0.
- 동 폴백(다른 동 후보)은 자기 동이 아니라 anchor 동의 가격계수를 받는다(근사).

## 7. 남은 실행 액션 (데이터 2개)

→ 업종(L1)×동 실측 건단가로 자동 승격 (하드코딩 표 대체)

### 7-2. 카카오 메뉴가 추출 — 가게 개별 실측화 (크롤 머신에서)

```bash
# 1) 스키마 확인 (가격 필드가 어디 있는지 리포트만)
python scripts/prep/extract_kakao_menu_price.py --probe --limit 500
# 2) 본 추출
python scripts/prep/extract_kakao_menu_price.py
# 3) 생성된 output/stats/poi_menu_price.json 을 시뮬 레포 output/stats/ 로 복사
```
