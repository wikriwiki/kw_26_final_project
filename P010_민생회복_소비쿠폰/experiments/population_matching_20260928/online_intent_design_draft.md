# 공통 LLM 판단을 이용한 온라인·오프라인 선택 경로 설계 초안

작성일: 2026-09-28 KST. 상태: **읽기 전용 소스 감사와 후속 설계 제안**. 이 문서는 실행 코드, 완료된 실험, 모델 서버, 그래프를 변경하지 않는다. 새 모드가 구현되거나 검증됐다는 뜻도 아니다.

## 결론

완료된 여섯 정책 기준선에서 기록된 `cm_online_share=0.7465`는 엔진이 계획 소비를 나누는 배분율이다. **실제 온라인 거래 비중이 74.65%였다는 관측값이 아니다.** Stage1의 온라인 선택을 그대로 반영한 결과도 아니다. 현 기본 분기는 소상공인 사용처 수준 보정의 나머지를 온라인 합계로 기록한다. 여기에는 개념상 대형 오프라인 매장 등 소상공인 외 소비와 실제 배송 주문이 혼재한다.

온라인 선택을 범용 프롬프트의 시민 판단으로 옮기려면, ① 소비 총액 수준 교정과 채널 선택을 분리하고, ② 실제 온라인과 소상공인 외 오프라인을 다른 속성으로 기록하며, ③ 온라인 주문에도 계획과 실행 영수증을 부여하는 별도 모드가 필요하다. 기존 결과와 새 모드의 차이는 **프롬프트와 엔진 구조의 차이**이므로, 공통 프롬프트만의 효과라고 부르면 안 된다.

## 현재 값과 의도가 흘러가는 경로

### 1. 0.7465의 주입 위치

`consumption.py:60`의 `ONLINE_SHARE_CAP` 기본값은 0.85, `:68`의 `ELIGIBLE_SHARE_SEOUL` 기본값은 0.2535다. 후자는 주석상 서울 소상공인 매출 수준을 전체 소비 앵커에 맞추는 교정값이며 실제 전자상거래 비중을 직접 추정한 값이 아니다. 주석의 매출·인구 산출 과정을 이 문서에서 원자료와 독립 재검증하지는 않았다.

거래가 있는 날의 기본 경로(`EXP_SPLIT_ANCHOR` 미활성)는 `:1025~1028`에서 다음을 수행한다.

```text
_off = 1 - ELIGIBLE_SHARE_SEOUL
_online_src = "seoul_smallbiz"
_online_rate = clamp(_off, 0, ONLINE_SHARE_CAP)
```

기본값이면 `_online_rate=0.7465`다. `run_simulation.py:512`가 Stage1의 `online_share`를 전달하더라도 **이 분기에는 그 필드를 사용하는 계산이 없다**. 전달되는 `spending_level` 역시 읽은 함수 본문의 배분 계산에서는 사용되지 않는다. 매개변수 주석의 “소비수준을 우선한다”는 설명을 실제 구현 증거로 쓰지 않았다.

`EXP_SPLIT_ANCHOR=1`이면 `consumption.py:996~1024`에서 다른 경로가 열린다. 소비 앵커 수준을 `ANCHOR_OVERSTATE`로 낮춘 뒤, `1-online_share`를 `KEEP_MEAN`으로 나눈 편차로 `SHARE_BASE`를 조정한다. 따라서 이 경로는 **LLM 온라인 비율을 그대로 사용하는 모드가 아니고**, 앵커 교정과 배분 정규화를 함께 변경한다. scalar가 없으면 `split_base`가 되어 기준값에 머문다. 현재 `KEEP_MEAN` 기본값은 0.80으로, “측정 전 1.0”이라는 앞선 주석과 다르다. 설정값을 실제 실행 매니페스트에 보존해야 한다.

### 2. Stage1·Stage2 출력 계약

`stage1_intent.py:227~242`는 `online_share`를 선택 필드로 정의하며 의미는 “오늘 지출 중 배송으로 받는 몫”이다. 유효 범위는 0~1이고 validator가 값을 잘라내거나 파싱 불가 값을 `None`으로 처리한다. 따라서 파싱 이후 필드만 보아서는 원시 응답의 유효성을 판단할 수 없다.

v53 렌더된 공통 프롬프트에는 이 필드 출력 요구가 없다. 예시의 최상위 소비 판단은 `daily_propensity`다. 필드가 schema에 존재한다는 것과 모델이 일관되게 그 판단을 수행하도록 요청했다는 것은 별개다. 이 문서는 보존된 모든 시민의 최초 원시 응답에서 `online_share` 발생률을 새로 전수 집계하지 않았으므로, “모든 응답에 이 필드가 없었다”는 주장은 하지 않는다.

`Stage2Pick`(`stage2_poi.py:54~68`)에는 POI, 지출액, 만족도, 정책 결제액 등의 필드가 있지만 전자상거래 채널이나 온라인 주문 영수증 필드는 없다. 현재 Stage2 계약만으로 온라인 주문과 방문 구매를 동등한 대안으로 생성했다고 입증할 수 없다.

기존 `v5online`은 배송 주문을, `v5offsite`는 대형마트·백화점 등을 포함한 “동네 작은 가게 밖” 소비를 같은 이름 `online_share`로 묻는다. **두 프롬프트는 같은 추정량을 묻지 않는다.** 예시 scalar도 각각 들어 있어 예시 고정값 쏠림을 별도 점검해야 한다. 과거 모듈의 실험 성과를 적은 주석은 이번 원장 감사의 대체 근거가 아니다.

### 3. 계획액, 실행액, 저장액의 구분

`consumption.py:957~976`은 앵커·계획 지출 등에서 총액을 만든다. `:1035~1037`은 그 총액에서 온라인 계획액을 먼저 분리하고, 나머지를 POI 거래에 배분한다. 온라인액은 물품·판매자별 LLM 주문을 합산한 결과가 아니라 이 분배식의 산물이다.

`consumption.py:1093~1102`는 온라인 계획액을 자기 잔액으로 먼저 제한하고, 남은 잔액과 허용 정책 결제를 오프라인 거래에 배정한다. 오프라인액에는 추가 잔액 검사와 할인 정산 등이 작동한다. 반올림도 있다. `:1263~1267`의 배분율, 온라인 실제 차감액, 전체 실행액은 그래서 다른 변수다.

```text
계획 배분율 = cm_online_share
기록된 온라인 실행액 = cm_online_total
기록된 전체 실행액 = cm_today_total_incl_online
실행액 기준 온라인 몫 = 온라인 실행액 / 전체 실행액  (전체 실행액 > 0일 때)
```

위 마지막 비율은 분배율 0.7465와 항상 같지 않다. 온라인 소비와 비사용처 소비를 혼용한 현재 정의 문제도 남으므로, 마지막 비율조차 현실의 전자상거래 시장점유율이라고 바로 부를 수 없다.

중요한 추가 제한: `consumption.py:820~828`은 물리 POI 거래가 하나도 없으면 `no_commerce`로 조기 반환하고 `online_total=0`도 기록한다. **배송 주문만 하는 날을 독립적인 소비일로 표현하지 못하는 경로**다. 기존 상한까지 고려하면 현 모드로 전부 온라인인 선택을 검증하기 어렵다.

`run_simulation.py:617~622`는 POI 일정을 `write_plan`으로 저장하고 `:639~652`는 온라인 합계를 별도 인자로 `night_create_state`에 전달한다. `plan_writer.py:538~547`의 `INCLUDES` 지출 합계에는 방문 POI 거래가 들어가고, `:581~593`은 온라인액을 잔액·월 지출에 별도로 반영한다. 온라인은 개별 `INCLUDES` 주문 영수증으로 생성되는 것이 아니다. 실행기의 영수증 scope도 `all_modeled_offline_commerce_v1`이다.

## 최소 추가 모드 제안

### 적용 단위

새 명시적 선택값, 예를 들어 `online_allocation_mode=legacy_fixed | llm_channel_intent`를 둔다. 미지정은 기존 경로 그대로 유지하고, 미지원 값은 실패시킨다. 이는 아직 구현되지 않은 인터페이스 제안이다. 소비성향 신규 모드와 채널 모드는 별도로 선택·동결해야 한다.

첫 기술 검증에서는 Stage1에 **모든 정책에서 동일한** “오늘 직접 방문할 구매와 주문할 구매를 구분해 결정한다”는 계약을 추가할 수 있다. 시민의 필요·보유 물품·시간·이동 여건·배송 가능성·가격·개인 예산·정책의 실제 적용 조건에 따라 판단한다. 정책이 있다는 이유만으로 특정 채널이나 소비 방향을 정하지 않는다. 공통 문구에는 실측 효과, 목표 방향, 목표 비율, 평가표, 정답 예시를 전달하지 않는다.

scalar를 우선 사용하는 최소 버전이라면 의미를 **총 구매 계획액 중 실제 원격 주문 계획액**으로 고정한다. 0~1은 형식상 가능한 범위이며 목표값이 아니다. 온라인과 소상공인 외 소비를 같은 scalar에 섞지 않는다. raw 값이 누락·비유한·범위 밖이면 해당 최초 응답의 기술 실패를 기록하고, 자동으로 고정 0.7465를 채운 뒤 LLM 성공으로 집계하지 않는다. 이 scalar 버전은 채널 배분 기술 확인에 한정하며 개별 업종·판매자·정책 자격 효과 검증에는 부족하다.

실제 정책 검증까지 가는 최소한의 완성형은 Stage2 선택에 `channel=physical_visit | remote_order`와 주문별 물품·금액·판매자 또는 검증 가능한 채널 식별자를 추가하는 것이다. 두 채널을 같은 예산·동일한 물품 수요의 대안으로 비교한다. 온라인 전용 날도 별도 주문 원장으로 실행될 수 있어야 한다. 방문 여부와 매장 유형(`small_business`, 대형 소매 등)은 다른 속성이다. 대형 오프라인 매장을 온라인으로 바꾸어 기록하지 않는다.

회계 엔진은 선택된 계획을 예산·재고·배송·정책 자격의 사실 제약 안에서 정산한다. 모든 정책에 “온라인은 정책 결제 불가”를 고정하지 않고, 각 정책 입력의 검증된 채널·판매자·상품 조건을 적용한다. 모형에 없는 판매자·배송 조건을 LLM이 사실처럼 만들어 내는 선택은 관측 지원 부족으로 분리한다.

현재 사용처 수준 교정과 앵커 교정을 먼저 분리해야 한다. 채널 scalar만 연결하면서 `EXP_SPLIT_ANCHOR`를 켜면 총액 수준까지 바뀌어 채널 선택 효과와 혼동된다. 교정값이 필요한 경우, 정책 결과를 보지 않는 별도 기준 자료와 기준 표본으로 정하고 양팔 동일하게 얼린다. ON/OFF마다 평균을 다시 맞추거나 실측 정책 효과에 가까워지도록 비율을 재조정하지 않는다.

### 필요한 입력

- 시민의 실제 거주·이동 제약, 디지털 이용 가능성, 필요한 물품, 최근 구매·재고, 시간, 배송 가능 시점, 물품별 두 채널 가격·배송비·재고와 판매자 사실. 없는 입력은 미측정이라고 남긴다.
- 자기 잔액과 수입, 정책의 실제 수혜 자격·잔여 한도·허용 채널·판매자·품목·기간. 소득 분포를 맞춘 것만으로 복지·가구·카드 등의 수혜 자격이 맞았다고 간주하지 않는다.
- 개별 정책의 내용과 해당 시기의 배경은 별도 입력이며 공통 판단 프롬프트는 동일하다. 정책 평가용 실측값·허용 오차·모범 결과는 모델 입력 경로와 분리한다.

### 반드시 보존할 원장

- 첫 HTTP 요청·응답 원문, 공통 프롬프트/개별 입력 SHA, 모델 가중치 근거, decoding 설정·seed, 시민·초기 상태·정책·환경·소득/자격 입력 SHA, 실제 환경변수 값과 코드 바이트 SHA.
- Stage1 원시와 파싱 후 채널 판단, Stage2 주문·방문 원시 선택, 요청 금액·결제수단, 파싱/수리/재시도 내역. 범위 제한과 fallback을 원시 판단과 구분한다.
- 채널별 주문 영수증: 시민·날짜·주문 ID, 상품/업종 범위, 판매자 유형, 계획 금액, 총 매출액, 자기 결제, 정책 결제, 할인, 취소·축소·미실행 이유. 온라인도 방문 영수증과 같은 감사 수준으로 남긴다.
- 계획 분배율·최종 금액 비율·정책 적격 지출 비율을 각각 다른 필드로 보존한다. 전체 매출과 자기 지출은 분모가 다르므로 별도 합계로 유지한다. 전체 거래 = 온라인 + 오프라인, 자기 결제 + 정책 결제 + 할인 = 정산된 매출 등 정책별 회계 정의에 맞는 항등식을 검사한다.
- 방문 그래프·주문 원장·State 잔액이 이중 차감되지 않게 동일 거래 ID로 연결한다. 재시작 때 주문이 중복 생성되지 않도록 시민일 트랜잭션과 완료 관문을 유지한다.

## 사전등록 비교 조건

1. 먼저 공통 프롬프트를 고정한 **엔진 모드 비교**를 수행한다. 같은 시민·초기 상태·정책/환경·기간·재원·가격·모델/decoding 설정으로 기존 배분 모드와 새 채널 선택 모드를 비교한다. 소비성향 opt-in 모드·총액 앵커 변경까지 동시에 섞지 않는다.
2. 이후 한 엔진 모드를 고정하고 공통 프롬프트 후보를 비교한다. 이 단계에서만 프롬프트 차이로 생긴 성능 변화라고 범위를 좁혀 말할 수 있다. 정책 효과의 방향·크기 검증은 별도의 ON/OFF와 정합한 실측 정의가 필요하다.
3. 정책 후보·표본·기간·실측 지표·변환식·누락 처리·품질 관문을 최초 결과 전에 등록한다. 튜닝 정책과 홀드아웃 정책을 분리하고, 홀드아웃 실측값을 읽어 문구·상수·표본을 조정하지 않는다.
4. 실제 서울시민 20세 이상 범위 등 정한 모집단에 성별·나이·행정동·소득 정합을 확인한 새 표본을 사용한다. 현재 완료 여섯 정책의 소비10분위 표본은 이 새 네 축 요구를 충족한 표본이 아니다. 소득의 조건부 결합·전년 이월은 관측 사실과 구분해 가정을 표시한다.
5. 첫 원시 응답의 형식·의도 필드 충족률, 주문/방문 지원 자료의 포착률, 회계 항등식, 재시도·장소/금액 수리율을 기술 관문으로 둔다. 최종 성공률만으로 첫 응답의 형식 안정성을 가리지 않는다.
6. 채널 방향 판단은 원시 선택, 제약 적용 후 실행, 정책 결제별로 분리한다. 실제 외부 실측과 모집단·기간·거래/매출 분모가 맞지 않는 숫자는 탐색적 병렬 수치로만 제시하고 정확도 오차·적중률로 채점하지 않는다.
7. 표본 확대는 관측 희소성에 도움이 되지만, 온라인/비사용처 혼용이나 정책 자격·상품/업종 매핑 누락을 해결하지 않는다. 이 문제는 데이터와 구조를 먼저 고쳐야 한다.

## 아직 확인하지 못한 부분

완료 프로세스의 정확한 EXP 환경변수 값, 시민별 최초 완성 HTTP 입력의 온라인 관련 내용, 현실 온라인 판매자·가격·배송 자료의 완결성은 여기서 확보되지 않았다. 소스에 적힌 과거 보정값 산출 근거도 독립적으로 재현하지 않았다. 이 문서의 새 모드·주문 schema·품질 문턱은 설계 제안이며 구현·실행·채택이 아니다. 기존 보고서 원수치와 완료 런은 그대로 유지한다.
