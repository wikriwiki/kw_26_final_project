# Colab 보조 GPU 연결 준비

상태: 2026-09-30 KST 설계·하드웨어 조회 노트북 준비. Colab 실제 GPU 할당, 모델 적재, 분산 실행 구현·배포·성능 측정은 아직 하지 않았다. 기존 Vast 본 실험은 이 준비 작업의 배포 대상이 아니다.

## 먼저 할 일

1. [Colab 구독 화면](https://colab.research.google.com/signup)에서 계정의 Pro+ 상품과 컴퓨팅 단위를 확인한다. 사용자는 상위 유료 상품을 구독할 의사를 밝혔으며 결제 완료는 아직 확인하지 않았다.
2. `no_smoking_gpu_check.ipynb`를 Colab에 업로드하고 GPU 런타임을 연결해 실행한다. 배정된 GPU 이름·실제 VRAM·설치 패키지 정보를 확인한다.
3. 동일 모델 적재와 소량 처리량 시험 후 실제 작업 배분량을 정한다. 노트북은 모델/실험을 설치하거나 실행하지 않는다.

[공식 FAQ](https://research.google.com/colaboratory/faq.html)에 따르면 유료 상품도 GPU 종류·가용성이 고정되지 않으며, Pro+ 연속 실행은 충분한 컴퓨팅 단위가 있을 때 최대 24시간이다. 따라서 연결 종료 후 Vast에서 이어갈 수 있어야 한다. 배포 시점에도 유료 컴퓨팅 단위 잔액 및 분산 작업에 관한 서비스 제한을 확인한다.

## 동일하게 유지할 실행 기준

- 기존 모델: `LGAI-EXAONE/EXAONE-4.5-33B-AWQ`
- 모델 revision: `31e6a965d0661bbe4a8b895e22a77f8271772ba0`
- 현재 Vast 관측 패키지: SGLang `0.0.0.dev11420+g6757c9f90`, torch `2.9.1`, transformers `5.8.0`
- 문맥 16,384, grammar backend `outlines`, 모델 서버 seed 42. 요청별 샘플링·JSON schema·토큰 한도도 기존 실행에서 전달한다.
- 활성 frozen v22 archive SHA256: `e6ab8021766613426a615de4f1322b2d315864b857080d4fe047c5e2e4277f7f`
- 활성 runtime manifest SHA256: `19f2a2eaf2587b8ee85da0e5f14278877a86fd4de543346bd31bb325383455eb`

위 값은 확인 당시 실행 기준이다. 구현 시 최신 `ACTIVE_DEPLOYMENT.json`과 실제 프로세스를 다시 대조한다. 다른 GPU/커널에서 비트 단위 동일 출력이 보장되는 것은 아니므로 실행 환경과 요청·응답 출처를 기록한다. 현재 Vast의 약 43GB 예약 메모리는 모델 가중치의 최소 VRAM 요구량과 같지 않다.

## 제안한 작업 분담

Vast의 한 감독 프로세스가 날짜·에이전트·단계·시도별 작업을 배정한다. Vast GPU가 앞 순서, Colab GPU가 뒤 순서를 맡는 정책을 사용할 수 있지만, 중앙 원장에서 할당 대상과 미완료 작업을 관리한다. 최종 배분은 각 GPU의 실측 처리량에 따른다.

- **Vast:** Dawn 입력 조회, 작업 원장, Stage1/Stage2 검증, Neo4j 트랜잭션과 outbox, metrics 봉인, 재시도 횟수, 날짜/야간 경계, Drive 백업의 유일한 소유자.
- **Colab:** 동일 모델로 배정받은 요청을 추론하고 응답·실제 설정·사용 토큰을 반환. DB 및 Drive 백업 자격증명을 받지 않는다.
- **날짜 경계:** 그날 1,154명 모두 `ok` 또는 `skipped`로 한 번씩 저장한 뒤 야간 처리를 완료하고 백업·다음 날짜로 넘어간다. 야간 추론 역시 두 GPU를 이용할 수 있으나 저장과 완료 판정은 Vast가 맡는다.
- **Colab 종료:** 작업 임대/heartbeat가 만료되면 미완료 요청을 Vast로 되돌린다. 늦게 온 응답에는 소유권 세대 번호를 대조해 중복 저장을 막는다. 첫 시도+최대5회 예산은 중앙 원장에 보존하며 연결 교체로 초기화하지 않는다. 이미 완료한 결과는 재계산하지 않는다.
- **통신:** 인증된 요청/응답 채널을 사용하며 Google Drive는 실행 중 작업 큐로 쓰지 않는다. 서버 접근 토큰은 코드·문서·노트북 출력에 넣지 않는다.

전체 시뮬레이터 두 개가 독립 DB를 갱신한 뒤 합치는 방식은 현재 cohort manifest, 실행 fingerprint, 재시도 원장, 야간 완료 마커 및 백업 경계와 맞지 않는다. 이번 구현은 중앙 DB를 유지하고 추론을 분담하는 방식으로 검토한다.

## 구현 및 검증 순서

1. Colab 실제 GPU에서 동일 모델/패키지 적재 가능 여부와 제한된 샘플 처리량을 확인한다.
2. 별도 런타임으로 요청 배정·응답 검증을 구현한다. 기존 source/execution fingerprint를 위조하거나 무시하지 않고 새 경로의 해시·활성 날짜·추론 장치 출처를 기록한다.
3. 중복 응답, 연결 종료, 재접속, 시도 예산, 마지막 에이전트와 야간 경계, 백업 중 요청 정지에 대한 합성 검사를 실행한다. 실제 모델 시험 출력은 본 결과에 합치지 않는다.
4. 현재 날짜 결과와 완전 그래프 복구점을 확보한 후 안전한 날짜 경계에서 적용한다. 현재 Python 프로세스에는 이 분산 기능의 hot reload가 없으므로, 필요하면 검증된 중단점에서 계산 프로세스만 인계한다. Vast 인스턴스/기존 모델을 무작정 재시작하거나 Day1부터 재계산하지 않는다.
5. 실제 두 GPU 처리량·실패율·단위 비용 및 Colab 재연결 뒤 진전을 측정한 뒤 종료 예상일을 갱신한다.

## 속도 추정의 범위

최근 온전한 Day6 실측은 계산 9.904시간 + 백업 등 0.728시간 = 약10.632시간이었다. Colab이 Vast와 같은 지속 처리량을 추가하고 주간·야간 추론을 모두 균등하게 나눌 수 있다고 가정하면 단순 하한은 `9.904 / 2 + 0.728 = 5.680시간/일`이다. 통신·작업 불균형·연결 종료·재적재·설치 시간은 포함하지 않았다. 실제 가속률이나 완료 날짜로 제시하지 않는다. 무조건 577명씩 나누면 느린 장치를 기다리게 되므로 고정 반분보다 처리량에 맞춘 배정이 필요하다.
